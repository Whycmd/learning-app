## 一、环境部署类

### ENV-01：MySQL 仅本地 socket 连接，TCP 默认不通

- **现象**：程序按 `127.0.0.1:3306` 连数据库失败；部分客户端无法连接。
- **根因**：MySQL 按"本地单机、不对外"部署，监听 unix socket（`/Users/junwang/.local/run/mysql.sock`），未启用 TCP 监听。
- **解决方案**：连接配置中使用 `socket` 字段指向 socket 文件路径；`config/db.json` 中同时保留 host/port 仅作兼容。所有运维操作带 `--socket=...`。
- **教训**：部署方式决定连接方式；连接失败先确认"监听的是 socket 还是端口"，不要只盯账号密码。

### ENV-02：MySQL root 密码的存放与读取

- **现象**：密码为自动生成，程序与脚本多处需要使用，硬编码不可取。
- **解决方案**：密码存于本地密码文件（`/Users/junwang/.local/mysql/.root_pw`）；`config/db.json` 用 `password_file` 指向该文件，程序启动时读取并去除空白/换行；Shell 中用 `$(cat 密码文件)` 引用。
- **教训**：敏感配置与程序配置分离；读文件后必须 trim，尾部换行/回车会导致认证失败。

### ENV-03：LocalAI 离线部署与免费模型不兼容

- **现象**：尝试用 LocalAI + 免费模型实现完全离线运行时，模型兼容性、资源占用不达预期。
- **解决方案**：放弃本地推理，改为"本地数据 + 在线 AI"架构，经 Node 网关调用免费的智谱 GLM-4-Flash。
- **教训**：离线推理需提前验证模型与运行时兼容性及硬件开销；免费在线模型在本场景性价比更高（代价是网络依赖，见 AI-03）。

## 二、编译构建类

### BLD-01：MySQL 头文件/库找不到

- **现象**：编译时 `mysql.h` 找不到；链接时 `library not found for -lmysqlclient`；运行时又报 `image not found libmysqlclient.21.dylib`。
- **根因**：MySQL 安装在用户目录（`/Users/junwang/.local/mysql`），不在编译器/链接器默认搜索路径；动态库运行时还需知道 dylib 位置。
- **解决方案**（编译命令三处显式指定）：

```bash
clang++ -std=c++17 -O2 -Wall -Wno-unused-parameter \
  -I/Users/junwang/.local/mysql/include \
  src/main.cpp -o build/eng_app_server \
  -L/Users/junwang/.local/mysql/lib -lmysqlclient \
  -Wl,-rpath,/Users/junwang/.local/mysql/lib
```

- **教训**：自包含安装的三方库，编译期（-I）、链接期（-L）、运行期（rpath）三个路径都要覆盖。

### BLD-02：C++ include 相对路径约定

- **现象**：源文件包含头文件路径不一致导致编译失败。
- **解决方案**：源文件位于 `backend/src/`，头文件位于 `backend/include/`，统一用 `#include "../include/xxx.h"`。
- **教训**：目录约定一旦确定不再变动，避免出现多种相对路径风格。

## 三、HTTP 接口类

### HTTP-01：POST 测试必须携带 Content-Length

- **现象**：用原生 socket 向 C++ 服务发 POST 请求时，服务端一直等待或解析异常。
- **根因**：服务端依据 `Content-Length` 判断 body 是否接收完成；空 body 也需该头部。
- **解决方案**：POST 请求一律带 `Content-Length`（空 body 时为 `0`），如 `curl -X POST -H "Content-Length: 0"`。
- **教训**：手写 HTTP 解析严格依赖头部，测试工具越底层越要自己补齐协议要素。

### HTTP-02：响应必须包含 Connection: close

- **现象**：客户端收到响应后挂起、等待连接关闭。
- **解决方案**：每个响应输出 `Connection: close`，服务端发送完毕主动 `close(fd)`。
- **教训**：不支持 keep-alive 的服务器必须明确告知客户端连接策略。

### HTTP-03：掌握要求（会读/会写）以代码规则为准

- **现象**：AI 对同一知识点返回的"会读/会写"判定不稳定。
- **解决方案**：不信任 AI 返回值，由代码按难度判定：`difficulty >= 5 → 会读`，否则 `会写`。
- **教训**：影响出题分层等关键分支的判定，必须由确定性规则产出；AI 只负责内容生成。

### HTTP-04：API 新增返回字段后必须用 curl 验证 JSON 中字段真的出现

- **现象**：`GET /api/exercise/generate` 接口返回 `"exercise_types":[]`，但测试用例期望有内容。
- **根因**：`QuestionService::GenerateResult.exerciseTypes` 字段在构造函数里初始化为空数组后，**代码里从未给它赋值**。handler 层序列化了这个空数组，但底层 service 从未填充。
- **排查**：翻查 `question_service.h` 发现 generate() 方法里根本没有对 `exerciseTypes` 的赋值语句；AI 返回的 JSON 解析后只填了 exercises 数组，漏提 exerciseTypes。
- **解决方案**：在 generate() 返回前，遍历 AI 返回的 exercises 数组，提取每道题的 `type` 字段去重后赋值给 `exerciseTypes`；若 AI 没返回 type 字段，按 mode 给兜底默认值（weekly 6 种、daily 3 种）。
- **教训**：API 返回 JSON 的"字段名存在"≠"字段值有内容"。新增返回字段后，必须写一条 curl + python3 -m json.tool 的手动验证，确认字段值真的非空。

## 四、并发与崩溃类

### CRS-01：浏览器操作触发后端进程崩溃（重点）

- **现象**：浏览器中切换页面（尤其从学情中心点击其他页面）后，8088 服务不可用；进程以 SIGABRT/SIGBUS 退出。**串行 curl 反复测试均正常，无法复现**。
- **诊断过程**：
  1. 查看 macOS 崩溃报告（`~/Library/Logs/DiagnosticReports/eng_app_server-*.ips`），用 Python 解析其中的 faultingThread 调用栈；
  2. 崩溃栈集中在：`mysql_real_query → cli_read_query_result → end_server → SSL_free / free → abort`，均为**堆损坏**特征；
  3. 用并行 curl（`for ... curl &; wait`）成功复现，确认与并发相关。
- **根因**：HTTP 服务为**每连接一个线程**（`std::thread(...).detach()`），而所有线程共享同一个 `MYSQL*` 连接，存在三个叠加问题：
  1. 单连接非线程安全，并发查询直接破坏内部状态；
  2. libmysqlclient 要求每个使用线程先 `mysql_thread_init()`，未初始化时其线程局部存储在并发下损坏；
  3. 本地连接协商了 SSL，连接重建路径上的 `SSL_free` 触发 OpenSSL 堆损坏；废弃的 `MYSQL_OPT_RECONNECT` 会放大该问题。
- **解决方案**（`backend/include/db.h`，三项同时生效）：
  1. 用 `std::recursive_mutex` 串行化 `query()`/`exec()`/`transaction()`（递归锁兼容事务内嵌套调用）；
  2. 每个线程首次使用前调用 `mysql_thread_init()`（thread_local 守卫）；
  3. 移除 `MYSQL_OPT_RECONNECT`，本地 socket 连接设 `SSL_MODE_DISABLED` 禁用 SSL；连接丢失仍由 2006/2013 错误分支显式重连。
- **验证**：5 轮 × 12 并发 DB 请求 + 3 轮 × 8 混合并发（页面/接口/字体）进程全程存活；浏览器逐页切换正常；全量回归 285 项通过。
- **教训**：
  - 串行测试无法暴露竞态——涉及多线程的改动必须用**并发压测 + 浏览器实测**双重验证；
  - 崩溃先看系统崩溃报告，调用栈能直接区分"业务逻辑错"与"堆损坏/线程安全问题"；
  - C API 库的线程安全要求（每线程初始化、句柄不共享）必须在集成时逐条满足。

## 五、C++ 后端经验类

### CPP-01：thread_local 上下文默认值必须在 beforeDispatch 中显式设置

- **现象**：新增 `RequestContext::currentUserId()` 后，未登录请求返回用户 ID = 0（未初始化值），导致所有查询 SQL 变成 `user_id=0`，全部查不到数据。
- **根因**：C++ `thread_local` 变量在首次线程创建时由运行时初始化为 0，但业务语义上「未登录」应映射到 `GUEST_USER_ID=1`（游客专用 ID），两者不等。
- **解决方案**：在 `HttpServer::beforeDispatch_` 回调入口强制赋值：
  ```cpp
  int uid = Auth::resolveUserId(req);
  if (uid < 0) uid = GUEST_USER_ID;   // token 无效 → 游客
  RequestContext::setCurrentUserId(uid);
  ```
- **教训**：全局上下文变量的默认值必须等于业务上的「无状态」语义值；不能依赖语言运行时零初始化。

### CPP-02：跨用户固化复用需两条路径统一复用同一 helper

- **现象**：实现 solidifyOne 时补了跨用户查重，但 solidifyBatch（批量一键固化）路径完全遗漏，导致批量录入时仍会重复调 AI。
- **根因**：solidifyOne 和 solidifyBatch 是两条独立代码路径，初期只在单条路径实现，未抽象为公共 helper。
- **解决方案**：将跨用户查重逻辑抽为 `tryCrossUserCache()` 公共 helper，两条路径均调用：
  - solidifyOne：直接调用 `tryCrossUserCache`；
  - solidifyBatch：在组批发给 AI 前，逐条先过 `tryCrossUserCache`，命中的计入成功数并从 needAi 列表剔除，只剩未命中条目进入 AI 调用。
- **教训**：涉及多条执行路径的功能（单条/批量、同步/异步），设计时先列出所有路径，确保每个路径都经过同一入口；抽象 helper 前先枚举完整调用图。

### CPP-03：动态拼接 user_id 时严格区分整数与字符串来源

- **现象**：越权访问漏洞——`handleKpSolidifyAll` 批量取知识点时 SQL 为 `SELECT * FROM knowledge_points`，未加 `AND user_id = ?`，导致任意用户可读取全部用户的知识点。
- **根因**：service 层 `user_id` 已参数化，但 main.cpp 中直接操作 DB 的 handler 函数仍使用硬编码 `WHERE user_id=1`，漏加当前用户过滤。
- **解决方案**：
  1. 所有 handler 中直接拼 SQL 的场景，统一使用 `RequestContext::currentUserId()` 获取当前用户；
  2. 用户 ID 为整数，直接 `std::to_string(uid)` 拼接即可，**无需** `Db::escape()`（整数无注入风险）；
  3. 字符串输入（如用户名）才必须用 `Db::escape()`。
- **教训**：认证系统接入后，必须全量扫描所有 SQL 拼接点；整数上下文值可安全直接拼接，字符串输入一律 escape。

### CPP-04：TSV/CSV 解析用 result.size() + 1 >= max_cols 替代手动计数

- **现象**：`splitTab(line, 7)` 吞掉第 7 列（f_c1 频率），EFLLex 加载从预期 15,281 行 → 仅 10,140 条（近 35% 丢失）。
- **根因**：原始代码手动 `size_t col` 计数 + `col >= max_cols - 1` 判断 + `break` 前先 `cur.clear()`，导致最后一列在 break 时被清空且未 push_back。双重 bug：off-by-one + clear 时机。
- **解决方案**：用 `result.size() + 1 >= max_cols` 判断"还能 push 吗"；能则 merge tab 到 cur，不能则 push_back + clear；循环结束后再 push_back 最后一段。彻底消除手动计数变量。
- **正确实现**：
  ```cpp
  for (char c : line) {
    if (c == '\t') {
      if (result.size() + 1 >= max_cols) cur += c;  // 合并剩余
      else { result.push_back(std::move(cur)); cur.clear(); }
    } else cur += c;
  }
  result.push_back(std::move(cur));  // 最后一段必须 push
  ```
- **验证**：修复后 EFLLex 加载 **13,546** 词条（sophisticated→C1 正确），与原始 TSV 数据吻合。
- **教训**：手动计数变量容易产生 off-by-one bug；用 `result.size()` 推导比独立计数器更安全可靠。

## 六、AI 与后端经验类

### AI-01：禁止切割提示词分段调用再拼接

- **现象**：AI 答案冗长、各板块前后逻辑不搭。
- **根因**：软件将用户写好的整段提示词拆散，分多次调用 AI 后拼接答案，失去整体连贯性。
- **解决方案**：按用户六板块完整叙述（核心含义与例句／词根词源／同源词汇／典故俗语与固定搭配／同义词辨析／补充知识）**一次构造、一次请求、一次完整返回**；批量与单条固化统一该结构。
- **教训**：提示词是一个不可分割的整体，工程实现不能为"省事/分段"破坏其完整性。

### AI-02：AI 对不适用项返回"无此内容"空话

- **现象**：规则要求"不适用可略过"，AI 仍返回 "There are no allusions..."、"No phrase analysis needed" 等内容，污染文档。
- **解决方案**：
  1. 提示词强化：明确"留空/省略，禁止输出 无/没有/no/none/not applicable 类说明"；
  2. 代码兜底：入库前归一化（小写、仅留字母数字），匹配 `there is/are no...`、`no...needed/applicable` 等结构性空话则跳过不入库。
- **教训**：对大模型的"省略"指令不会被 100% 遵守，关键规则需在代码层再设一道确定性过滤。

### AI-03：在线 AI 网络依赖导致的超时与偶发失败

- **现象**：全套连跑时偶发网关超时失败；单次固化耗时可接近 2 分钟。
- **解决方案**：
  1. 区分失败性质：单独重跑能通过即网络瞬时抖动，非代码缺陷；
  2. AI 网关设 `responded` 标志，超时后不得重复写响应头（防止崩溃）；
  3. 涉及 AI 的接口与测试客户端超时由 90s 放宽至 **130s**；
  4. 固化前做精确查重，命中已有词条直接合并，免一次 AI 调用；
  5. 彻底方案（待办）：指数退避重试 + 本地缓存 + 断网规则兜底。
- **教训**：在线 AI 的延迟与失败要当正常情况设计；先做"少调一次是一次"的优化（查重），再做重试与降级。

### AI-04：AI 输出为字符串数组时的解析兼容

- **现象**：同源词汇/典故/同类词语等字段，AI 有时返回字符串、有时返回字符串数组，旧解析只认字符串会丢数据。
- **解决方案**：`flexStr()` 容错取值：字符串直接用；数组则逐元素用换行拼接（元素非字符串时降级序列化），再统一入库。
- **教训**：与大模型交互的数据结构必须做"多形态兼容"，按字段语义归一化后再存储。

### AI-05：AI 会"创造性润色"standard_content，查重必须同时匹配 user_input_content

- **现象**：用户录入 "start" 固化后，再录入同一单词会生成两条固化记录（没命中查重合并）。
- **根因**：AI 在固化时会对 `standard_content`（规范词条）做"创造性解读"——"start" 可能被润色为 "venture" 或 "strategic"。查重逻辑只匹配 `standard_content`，完全忽略用户原始输入 `user_input_content`，导致明明是同一单词却无法命中查重条件。
- **排查**：翻了两条记录的数据库，发现 `user_input_content="start"` 但 `standard_content` 不同（一个 start、一个 venture）。用 `SELECT standard_content, user_input_content FROM knowledge_points WHERE id IN (...)` 对比确认。
- **解决方案**：两处查重 SQL（`tryCrossUserCache` 和 `applySolidify`）都加上 `OR user_input_content` 条件：
  ```sql
  WHERE (standard_content = ? OR user_input_content = ?)
    AND is_solidified = 1 AND id <> ?
  ```
- **验证**：修复后 stage2 查重用例从 30/31（1 个失败）→ **31/31 全部通过**。
- **教训**：AI 输出的 `standard_content` 是"AI 理解后的版本"，而 `user_input_content` 是用户原始输入。涉及查重/去重的场景，必须同时匹配两者，以用户原始输入为更稳定的锚点。

## 七、工具与流程类

### TOOL-01：浏览器截图工具超时/不可用

- **现象**：截图调用长时间超时；标签页离屏或渲染器节流时直接报不可用。
- **解决方案**：不依赖截图时改用 `browser_evaluate` 读取计算样式（字体、配色、圆角、阴影）做客观视觉审计；确需截图时读返回结果中的本地图片路径再用文件工具查看，且只截视口不截全页。
- **教训**：视觉验证不一定靠截图，计算样式审计更稳定、可重复、可量化。

### TOOL-02：后台任务包装器可能连带杀进程

- **现象**：用后台任务方式启动的服务，在包装器监控器异常退出（约 1–2 分钟）后，整组任务被终止。
- **解决方案**：需要长期运行的服务改用 `nohup 命令 > 日志 2>&1 & disown` 启动，使其脱离会话与任务包装器的进程组。
- **教训**：分清"调试用后台任务"与"生产级常驻服务"；后者必须脱离父进程生命周期。

### TOOL-03：崩溃报告（.ips）解析方法

- **问题**：`.ips` 文件是 JSON 但头部多一行元数据，直接解析报错。
- **解决方案**：跳过首行后按 JSON 解析；取 `faultingThread` 索引找到崩溃线程，结合 `usedImages` 的 imageIndex 还原每个帧的动态库名与 `symbol`。
- **教训**：macOS 崩溃报告是定位原生程序问题的第一手证据，解析方法应固化复用。

### TOOL-04：后端调试三步曲 — 先确认端口空再启动新进程

- **现象**：明明编译了新二进制（`strings build/eng_app_server | grep "DEBUG"` 能看到新 debug 字符串），curl 请求却打到旧代码（无 DEBUG 日志、exercise_types 字段为空）。
- **根因**：之前的 `./backend/build/eng_app_server &` 进程没杀干净（旧 PID 7201 一直在 8088 端口监听），新进程因端口被占用直接 exit，但我没检查端口状态就误以为新进程已启动。
- **排查**：`lsof -ti:8088` 输出 PID 7201；`strings /proc/7201/exe 2>/dev/null | grep "DEBUG"` 或 `ps -p 7201 -o comm=` 确认是旧二进制在跑。
- **解决方案**：后端调试固定三步曲：
  ```bash
  pkill -9 -f eng_app_server 2>/dev/null
  sleep 2
  lsof -ti:8088 | xargs -r kill -9  # 端口残留兜底清理
  # 确认 lsof -ti:8088 为空后，再启动新进程
  ```
- **教训**：编译成功 ≠ 运行的是新代码。每次改完代码重启后端前，必须先确认监听端口上没有旧进程残留。

## 八、前端 TTS 经验类

### TTS-01：speechSynthesis 状态检查不可省略

- **背景**：v1.2.0-T006 在 `tts.js` 中调用浏览器原生 `SpeechSynthesis` API 实现朗读。
- **问题**：部分浏览器（或无语音支持的環境）中 `speechSynthesis` 对象存在但实际不可用，直接调用会静默失败或抛出异常。
- **解决方案**：在 `speak()` 入口增加 `'speechSynthesis' in window` 检查，不可用时输出 warning 并提前返回；同时使用 `cancel()` 先停止当前播放，再创建新 `SpeechSynthesisUtterance`。
- **教训**：Web API 能力检测必须先于使用；`in window` 是最轻量的特性检测方式。

### TTS-02：预留 speakRemote 接口便于后续接入后端 TTS

- **背景**：T006 当前仅使用浏览器原生 TTS，但需求要求「保留后续接入后端 TTS 服务的渠道」。
- **设计**：在 `tts.js` 中暴露三个方法 `{speak, stop, speakRemote}`，其中 `speakRemote(word, opts)` 当前直接 delegate 到 `speak(word, opts)`，但内部留有 TODO 注释和独立接口，后续只需将函数体替换为 fetch 调用即可。
- **教训**：扩展点应在开发初期预留，避免后期重构接口；IIFE 封装导出的公共模块天然适合这种渐进式增强。
