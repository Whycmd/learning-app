## 三、任务分解

### T1 生产端口与静态资源优化

1. 新增 `docker-compose.prod.yml`：仅覆盖 `app` 的 `ports` 为 `80:8088`、`restart: always`，并加容器日志上限（如 `max-size: 10m`、`max-file: 3`）；`db` 不向宿主机开放 3306。
2. 新增 `.env.prod.example`，写明必填项（`MYSQL_ROOT_PASSWORD`、`MYSQL_PASSWORD`、`ZHIPU_API_KEY`）与生成方式。
3. `Dockerfile` 构建阶段预压缩静态资源，保留原文件；本地开发无 `.gz` 时按原样返回。
4. 修改 `handleStatic()`：按 `Accept-Encoding` 选择 `.gz`；HTML 返回 `Cache-Control: no-cache`，css/js 返回 `no-cache`（**v1.5.3-T003 已改，勿回退为长缓存**），字体 `public, max-age=2592000`；补 `Vary: Accept-Encoding`。
5. 本地自测：带 gzip 头与不带 gzip 头各请求一次首页、`style.css`、一个 js 文件，校验状态码、`Content-Encoding`、`Cache-Control` 与内容长度。

### T2 评审账号与演示数据

1. 新增 `scripts/seed_demo.js`，连接现有库，按用户名幂等创建 `templecat` / `wordninja` / `goldfox`（原 `demo1` / `demo2` / `demo3` 自动改名迁移；同一密码，密码写入材料清单，不写入公开页面）。
2. 每个账号预置同一套数据：
   - 1 个「正在执行」课规 + 2 个其他课规；
   - 8 个已固化知识点（含定义与精讲正文，供 L1 秒回）；
   - 4 条错题，覆盖释义 / 拼写 / 搭配 / 语法四类错因；
   - 3 条重练队列、8 条学情、近 7 天 21 条复习日志（让学情周报有数据）；
   - 金桂 120。
3. 幂等规则：账号与词条按唯一键更新；学习进度、错题、课规只在首次（该用户无课规）写入，重复执行不新增、不重置已有进度。
4. 自测：空库执行一次 → 3 个账号可登录且首页概览有数；再执行一次 → 各表行数不变。
5. 生产用法（容器内）：`docker compose --env-file .env.prod -f docker-compose.prod.yml exec app node scripts/seed_demo.js`，校验加 `--verify`。

### T3 线上部署与网络验收

1. 阿里云 99 元 ECS（2 核 2G / 3M / 40G，Ubuntu 24.04）；安全组只开 22、80。
2. 安装 Docker 与 Compose，增加 2G swap；拉取代码。
3. 配置 `.env` 后执行 `docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build`；启动后执行 `exec app node scripts/seed_demo.js` 与 `--verify`。
4. 验收：
   - `GET /api/health` 返回 200；
   - 手机 4G（关闭 WiFi）打开 `http://IP/`，首屏可交互；
   - 3 个账号分别登录成功；
   - AI 讲解 1 次成功，复习 1 题、错题本 1 条可见；
   - 容器重启策略为 `always`。
5. 评审期保障：保持运行，接入阿里云云监控；每日备份沿用 `OPS-BASELINE`；每天自检 `/api/health`。

### T4 申报材料包

1. 3 个关键任务 TRAE Session ID：AI 讲解与精讲固化、课规与学情周报、错题归因与重练。
2. 开发过程截图不少于 3 张；产品截图 1–3 张（首页、AI 讲解、错题本或周报）。
3. 1–5 分钟演示视频：脚本分镜 + 旁白，覆盖「查词讲解 → 加学习 → 复习小测 → 错题重练 → 周报」。
4. 一页说明：体验链接、3 组账号、已知限制（无 HTTPS、AI 依赖网络、移动端为桌面版兜底）。
5. 材料清单落在本目录，逐项写明文件路径或链接。

### T5 全量回归与线上复验

1. 本地执行 `node tests/run_all.js`，含新增 `stage35`，要求全部通过。
2. 线上复验 T3 全部验收项；评审开始前再跑一次首屏与登录。
3. 文档同步：`产品现状`、`核心参数`、`README`、`开发者使用指南`、`人工修改渠道集合`；登记 `待审查登记.md`。
4. 任务收口后按 `06-部署.md` 判定版本号；本任务不提前升位。

## 五、风险与应对

| 风险 | 应对 |
|---|---|
| 2G 内存编译或运行 OOM | 部署前加 2G swap；串行构建；容器日志限 10m×3 |
| 3M 带宽首屏慢 | 预压缩 + 缓存头，目标把首屏传输量压到约 500KB；评审前实测 |
| 80 端口被运营商或企业网拦截 | 提前用手机蜂窝网络实测；若不通，临时改用 8080 并在材料中写明端口 |
| 评委多人共用账号互相干扰 | 3 个独立账号；种子脚本可随时重跑恢复 |
| 评审期宕机 | `restart: always`、云监控、每日备份、每天自检 `/api/health` |
| 无 HTTPS 的观感与能力限制 | 已核实全站仅复制功能依赖安全上下文且有 `execCommand` 兜底；材料说明演示性质，不涉及支付与真实敏感数据 |
| 本地无 `.gz` 文件导致实现分支未覆盖 | `handleStatic` 仅在 `.gz` 存在时启用；本地用 Docker 构建镜像做一次端到端验证 |
| 构建镜像缺少 gzip 命令 | 构建阶段检查并按需安装；失败则改为在仓库内生成 `.gz` 后提交（二选一，不引入运行时依赖） |
