## 二、每日检查项

按 A→E 顺序执行，任一项不通过即进入第四节异常处理。

| 序号 | 检查项 | 方法 | 通过标准 |
|---|---|---|---|
| A | 服务探活 | 第三节只读探活命令 | `health 200`、`home 200`、`status":"ok"`、`"db":true` |
| B | 首页可打开 | 浏览器访问根路径 | 首页完整渲染，5 个入口可见，无白屏/报错弹窗 |
| C | 3 账号登录 | 浏览器分别登录 3 个演示账号 | 均能进入首页并显示预置数据（复习、小测、课规） |
| D | AI 讲解 | 登录后输入 `abandon`、`resilience` 各一次 | `abandon` 秒回（L1 命中）；`resilience` 30 秒内返回完整正文（L2） |
| E | 日志与磁盘 | 第三节日志/资源命令 | 无持续报错；磁盘使用率 < 80%；内存无持续增长 |

### 明细与异常指向

- **A 探活**：`"ai":false` 或 `"ai_degraded":true` 只影响 AI 功能，不阻断登录与学习；`"db":false` 为一级故障，直接走第四节。
- **B 首页**：重点确认 `/static/*.css`、`/static/*.js` 同为 200，避免样式丢失被误判为功能故障。
- **C 登录**：三个账号数据互相隔离，需逐个登录；登录失败先看是否仅单个账号（账号/数据问题）还是全部（会话/服务问题）。
- **D AI 讲解**：`"ai_tasks":{"failed":N}` 持续增加说明任务在失败重试，记录 N 值变化；冷却期（单模型连续失败 3 次 → 600 秒）内会出现"暂时不可用"提示，属预期降级。
- **E 日志与磁盘**：日志按 10MB × 7 份轮转，容量可控；重点是磁盘增量（数据库 + 备份 7 天）与内存是否被打满（服务器 1.7G 可见 + 2G swap，接近上限时响应会明显变慢）。

## 四、异常处理顺序

严格自上而下，前一步未排除不进下一步，避免盲目重启扩大影响。

1. **确认范围**：换网络（如手机 4G）复测一次，排除本地网络/浏览器缓存。
2. **看 A 项探活**：区分"入口不通"（80/首页失败）与"服务在但功能异常"（health 200 而某功能失败）。
3. **看容器状态**：`docker compose ... ps` 与 `docker logs --tail 200 elf-app`，定位是 `elf-app`、`elf-db` 还是端口占用。
4. **看资源**：磁盘、内存、swap；磁盘满或内存耗尽先按第五节清理/释放，不要直接重启数据库。
5. **区分 AI 故障与主体故障**：仅 AI 失败（`"ai":false` / 讲解超时）时按降级处理，不重启整套服务，记录时间点与 `failed` 计数，等冷却期结束复测。
6. **单容器重启**：仅重启 `elf-app`（见第五节）。
7. **整套重启**：单容器无效时 `up -d` 重建。
8. **回滚**：重启后仍不可用，按第六节回滚。
9. **记录与上报**：每一步记录时间、命令、现象、结果；影响评审的故障立即告知用户。

禁止项：使用会匹配到自身命令行的 `pkill -f`（部署期曾因此导致 SSH 自断，exit 255）；未确认备份可用前不要做数据库恢复。

## 五、重启步骤

```bash
cd /opt/english-app

# 1) 先看状态
docker compose --env-file .env.prod -f docker-compose.prod.yml ps

# 2) 只重启应用（首选，影响面最小）
docker compose --env-file .env.prod -f docker-compose.prod.yml restart elf-app

# 3) 应用重启后复查
curl -sS -m 10 http://123.56.205.221/api/health

# 4) 整套重建（第 2 步无效时）
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d

# 5) 若 80 端口被残留进程占用，先确认占用者再释放
ss -lntp | grep ':80 '
fuser -k 80/tcp   # 仅在确认是遗留探针/旧进程时使用
```

说明：`restart: always` 已配置，容器异常退出会自动拉起；进程内崩溃优先看日志而不是反复手动重启；数据库容器不做单独重启，除非 `elf-db` 明确 unhealthy。

## 六、回滚步骤

> 前置条件（用户已裁定执行，**服务器上尚未执行**）：服务器未使用镜像仓库，回滚依赖本地留底。若未留底，只能用仓库代码重建，回滚点不可控。以下第 0 步须在 11/24 前手工执行一次并确认产物存在。

**第 0 步：赛前留底（一次性）**

```bash
cd /opt/english-app
tar czf /opt/english-app_snapshot_$(date +%Y%m%d).tar.gz --exclude=mysql_data .
docker images | grep -i elf-app
docker tag <当前 elf-app 镜像ID> elf-app:rollback-$(date +%Y%m%d)
```

**回滚（评审期故障时）**

```bash
cd /opt/english-app
docker compose --env-file .env.prod -f docker-compose.prod.yml down   # 不加 -v，保留 mysql_data
mv /opt/english-app /opt/english-app.broken
mkdir /opt/english-app && tar xzf /opt/english-app_snapshot_YYYYMMDD.tar.gz -C /opt/english-app
cd /opt/english-app
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --build
curl -sS -m 10 http://123.56.205.221/api/health
```

**数据回滚（仅在数据被破坏时，破坏性操作，需用户确认后执行）**

- 备份位置：`backups/english_learning_daily_YYYYMMDD_HHMMSS.sql`，每日 03:00 自动生成，保留 7 天。
- 恢复前先把当前库导出一份留底；恢复会覆盖评审期产生的数据，非必要不做。
