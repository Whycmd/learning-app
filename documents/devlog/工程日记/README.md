## 二、写作规则

1. **人称**：“我”指项目开发者本人 Why；“助手”指 AI 协作方，不另取名。
2. **语言**：仿阿城。短句，多成语，幽默生动，通俗易懂；不仿古，优先让非技术读者读懂。
3. **开头**：先给一个具体画面或原话，直接进冲突，不写背景介绍。
4. **结构**：按时间线推进，轻小说式场景与访谈记录并行。
5. **引述**：原话只用真实出现过的句子；场景与动作可文学化，不虚构事件。
6. **技术**：正文说人话，关键技术细节放文末脚注，按 `[1]`、`[2]` 编号。
7. **篇幅**：每篇 800–1000 字；重要版本最多 2000 字。
8. **收尾**：单列「还没做完」，不粉饰。

## 三、写作模板

```markdown
# v1.x：一句短题

> 时间：YYYY-MM-DD ~ YYYY-MM-DD
> 版本：v1.x（补丁版本并入所属中版本）
> 状态：已完成 / 进行中 / 规划中

第一段：一个具体的画面或原话，直接进入冲突。

## 一、短题

事情怎么发生，我做了什么，助手做了什么。

## 二、短题

关键选择：有哪些选项，为什么选这个，代价是什么。

## 三、短题

转折或结果。

## 还没做完

未完成与局限，逐条写。

## 技术脚注

[1] 文件、命令或数据来源。
```

## 四、命名与归档规则

1. 文件名用 `v{中版本}.md`，例如 `v1.4.md`。
2. 补丁版本不单独建文件，内容并入所属中版本；`v1.4.1` 并入 `v1.4.md`。
3. 新中版本开工后再新建文件；规划期可先写对应 `v1.5.md`，并在状态中标注「规划中」。
4. 每新增一篇，同步更新本页索引。
5. 旧 `工作总结.md` 已拆分完毕并删除；后续只维护工程日记，不再保留双份正文。

---

## 五、附件规则

1. 截图、结构图放 `工程日记/assets/v{版本}/`，文件名用「日期-用途」，例如 `2026-11-07-word-export.png`。
2. 正文引用附件用相对路径；不写本机绝对路径。
3. 不放入真实 API Key、账号密码、个人金额、用户隐私数据。
4. 单张图片不超过 1 MB，能裁剪就裁剪。

---

## 六、事实边界

- 只写真实完成并核实过的代码、接口、页面与测试。
- 不把计划写成已完成，不虚构 bug、功能或验收。
- 人物统一写「我」与「助手」，不出现真实姓名。
- 版本状态与 `产品现状.md`、`工作计划/02-已完成任务摘要.md` 保持一致。
