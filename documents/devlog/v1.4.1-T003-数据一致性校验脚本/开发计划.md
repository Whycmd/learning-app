## 三、设计

### 3.1 连接与配置

- 默认读取 `config/db.json`：`socket`、`user`、`password_file`、`database`；
- 覆盖优先级：环境变量 `MYSQL_BIN` > `DB_SOCKET` > `DB_NAME` > 配置文件默认值；
- 默认 `MYSQL_BIN=/Users/junwang/.local/mysql/bin/mysql`（与现有测试套件一致；T011-T6 的 `tests/_env.js` 落地后统一改为其导出，避免二次分叉）；
- 连接失败（socket 不存在/服务未启动）→ 退出码 1，提示「MySQL 未启动，先执行 `bash scripts/start_mysql.sh`」。

### 3.2 检查清单（16 条关系，无外键，均为真实列名）

| # | 子表(列) | 父表 | 空值策略 |
|---|---|---|---|
| 1–5 | `kp_definitions` / `kp_collocations` / `kp_synonyms` / `kp_antonyms` / `kp_extras` 的 `knowledge_id` | `knowledge_points.id` | NOT NULL，全查 |
| 6 | `user_learning.knowledge_id` | `knowledge_points.id` | 全查 |
| 7 | `review_logs.knowledge_id` | `knowledge_points.id` | 全查 |
| 8 | `wordbook_entry.wordbook_id` | `wordbook.id` | 全查 |
| 9 | `wordbook_entry.knowledge_id` | `knowledge_points.id` | 全查 |
| 10 | `article_sentences.article_id` / `article_vocabulary.article_id` / `article_quizzes.article_id` | `articles.id` | 全查（合并为一条关系组） |
| 11 | `article_import_records.article_id` | `articles.id` | NULL 跳过 |
| 12 | `article_recommend_queue.article_id` | `articles.id` | NULL 跳过 |
| 13 | `solidify_job_items.job_id` | `solidify_jobs.id` | 全查 |
| 14 | `solidify_job_items.knowledge_id` | `knowledge_points.id` | 全查 |

**用户归属检查（单列一组）**：`knowledge_points` / `user_learning` / `review_logs` / `wordbook` / `daily_quiz` / `user_coin` / `user_coin_txn` / `user_seal` / `user_title` / `user_weekly_goal` / `user_sessions` / `articles` / `article_import_records` / `article_recommend_queue` 的 `user_id` → `users.id`。
- `users` 不存在 `id=1` 时，`user_id=1`（默认游客）单独汇总为 1 条「游客用户缺失」警告，不逐行计孤儿，避免报告噪音；
- `NULL` 值跳过（`articles.user_id`、`article_vocabulary.user_id`、`article_recommend_queue.user_id` 允许 NULL）。

**不做检查（多义引用，无法判定）**：`ai_tasks.ref_id`、`user_coin_txn.ref_id` —— 列内可指向不同业务表，误报率高，脚本内注释说明。

### 3.3 输出与退出码

- 控制台：每条关系一行（`关系名 | 孤儿行数 | 示例 id（默认 5 个）`），末尾汇总；
- `--json [路径]`：输出完整 JSON（关系名、行数、示例 id 列表、扫描/修复时间、库名、修复前后计数）；缺省路径 `logs/consistency_<YYYYMMDD-HHmmss>.json`；
- `--limit <n>`：示例条数，默认 5；
- `--fix`：**自动修复**（见 §3.4）；修复后再扫描一次，以修复后的结果决定退出码；
- `--help`：用法说明；
- 退出码：`0` 无孤儿（含修复后归零）；`2` 仍有孤儿；`1` 运行错误（连接失败、SQL 失败、参数非法）。

### 3.4 自动修复规则（`--fix`）

| 对象 | 规则 | 理由 |
|---|---|---|
| 16 条结构关系（子表 `knowledge_id`/`wordbook_id`/`article_id`/`job_id` 指向缺失父行） | `DELETE` 子表孤儿行（多表 DELETE + LEFT JOIN） | 父行已不存在，子行无法被任何业务读取，删除是唯一正确动作 |
| 用户归属组（`user_id` 指向不存在的用户） | 若 `users` 缺少 `id=1`（游客），按 `03_auth.sql` 约定自动创建游客行（`username='guest'`）；随后 `UPDATE ... SET user_id=1` | 用户数据不删；改挂游客可保留数据可用性 |
| 多义引用列（`ai_tasks.ref_id`、`user_coin_txn.ref_id`） | 不修复、不检查 | 语义不确定，误改风险高 |

- 默认**只报告不写库**；只有显式传 `--fix` 才执行写操作；
- 修复按关系逐条执行，每条记录「修复行数」，输出到控制台与 JSON；
- 修复不触碰非孤儿行（测试用行数快照断言）。

### 3.5 只读保证（默认模式）

- 默认模式仅 `SELECT` / `SHOW`；静态断言脚本中不含 `INSERT` / `UPDATE` / `DROP` / `ALTER`，`DELETE` 仅出现在 `fixOrphans()` 内且受 `--fix` 开关保护；
- 不修改任何表结构。

### 3.6 人工修改渠道

- 检查清单集中在脚本顶部 `RELATIONS` 数组（`{name, childTable, childCol, parentTable, allowNull}`），新增关系只改这一处；
- 连接参数在 `config/db.json`；示例条数/输出路径/是否修复走命令行参数。

## 六、风险与应对

| 风险 | 应对 |
|---|---|
| 本地 MySQL 未启动（实测 socket 存在但服务未运行） | 自测前 `bash scripts/start_mysql.sh`；测试先探测，未启动明确失败并提示 |
| `users` 无 `id=1` 导致游客数据全被计为孤儿 | 单独汇总为警告，不逐行计；`--fix` 仅在游客存在时改挂 |
| `--fix` 误删真实数据 | 只删「父行不存在」的结构孤儿；用户归属只改挂不删除；测试用探针行 + 行数快照双重断言 |
| 存量库已有孤儿 → 断言「全库为 0」会失败 | 测试只断言探针关系的增量与归零，不断言全库为零 |
| 套件编号与 v1.4.1-T001 计划的 `stage14_docker_assets.test.js` 冲突 | 本任务占用 `stage14_consistency`；T001 docker 资产套件最终定为 `stage16_docker_assets`（stage15 被 HTTP 加固占用） |
| 多义引用列误报 | `ai_tasks.ref_id`、`user_coin_txn.ref_id` 不检，脚本内注释 |
| 大表扫描耗时 | 数据量小（kp 千级以内）；单次 LEFT JOIN 聚合，`--limit` 只影响示例数 |
