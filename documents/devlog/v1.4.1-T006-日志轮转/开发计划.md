## 一、目标

为后端与 AI 网关日志增加按大小轮转：活动日志超过 10MB 时切分为 `.1`~`.7` 归档并保留 7 份，启动时异步清理超出保留份数的旧归档；轮转在后台执行，不阻塞服务启动，且日志与进程参数均不包含 API Key。

## 四、实现设计

### 4.1 配置 `config/log.json`

```json
{
  "max_size_mb": 10,
  "keep_files": 7,
  "check_interval_sec": 60,
  "files": ["eng_app.out", "backend.out", "localai.out", "log_rotate.out"]
}
```

- 日志目录解析优先级：命令行 `--dir` → 环境变量 `APP_LOG_DIR` → 环境变量 `LOCALAI_LOG_DIR` → 默认 `~/.local/log`。
- 默认值兜底：配置缺失或字段非法时回落 10MB / 7 份 / 60 秒，保证脚本可直接运行。

### 4.2 单文件轮转算法（copytruncate）

1. 读取活动文件大小，未达阈值则跳过；
2. 获取文件锁 `${file}.rotate.lock`（`wx` 排他创建），已有锁且未过期（5 分钟）则跳过；超过 5 分钟视为残留锁并清理；
3. 删除 `${file}.${keep}`（如 `.7`），将 `.6`→`.7`、…、`.1`→`.2` 依次后移；
4. 对活动文件做快照并写入 `.1.tmp`，`rename` 为 `.1`；
5. 将活动文件截断为 0，写入方继续向同一 inode 追加，服务不中断；
6. 记录一条轮转事件到 `log_rotate.out`（只记录文件名、大小、时间，不写日志正文）。

> 采用 copytruncate 的原因：现有日志由 shell 重定向或 Node 追加流持有文件句柄，直接 rename 会导致写入方继续写旧文件。copytruncate 是 logrotate 的标准做法。代价是“快照与截断之间”新增的极少量日志可能丢失；本应用日志量低，可接受，已在风险表登记。

### 4.3 启动清理

- 删除超出保留份数的归档（`.8`、`.9`…）；
- 删除超过 1 小时的 `.tmp` 残留；
- 删除超过 5 分钟仍存在的 `.rotate.lock` 残留；
- 清理与首次大小检查均在后台执行，不阻塞启动。

### 4.4 后台监控

- `node scripts/log_rotate.js --watch` 每 `check_interval_sec` 秒检查一次；
- 启动脚本以 `nohup … &` 拉起，PID 写入 `$RUN_DIR/log_rotate.pid`；
- PID 文件存在且进程存活时不重复拉起；
- `stop_all.sh` 根据 PID 文件停止 watcher；
- watcher 自身输出重定向到 `log_rotate.out`，该文件也纳入轮转清单。

### 4.5 不泄漏密钥

- 轮转脚本只读取文件大小，不读取、不打印日志正文；
- 不读取 `config/ai.json` 与密钥文件；
- 启动脚本不把 Key 写入命令行参数（维持现状）；
- 测试对宿主日志与进程参数做检查：若本机已配置 Key，断言日志中不含该 Key、运行进程参数中不含该 Key。

## 七、风险与应对

| 风险 | 应对 |
|---|---|
| copytruncate 快照与截断之间新增日志可能丢失 | 日志量低；在文档中注明；轮转事件记录时间与大小便于排查 |
| 多个 watcher 同时轮转导致归档错乱 | PID 文件防重复拉起 + 文件级排他锁 |
| 轮转时写入方仍持有文件句柄 | 使用 copytruncate 保持 inode，不采用直接 rename |
| 大文件快照占用内存/耗时 | 按记录大小分块流式复制，后台执行，不阻塞启动 |
| 容器内路径与宿主机不同 | 统一通过 `APP_LOG_DIR` 注入；容器内为 `/app/logs` |
| 密钥出现在轮转事件日志 | 轮转事件只记录文件名、字节数、时间，绝不记录正文 |
| Windows 原生模式 | 项目 Windows 仅支持 Docker；容器路径已覆盖 |
