## 一、v1.0：先把地基打牢

第一版没有「体验」可言，目标只有一个：把学习闭环跑通。共六个阶段。

**环境与数据库**。MySQL 8.0 装在本机，只监听本地 socket；Node.js 负责网关、脚本和 Word 生成；C++17 后端统一入口。建表统一 InnoDB、utf8mb4，不设外键，表间一致性由代码保证——这是 Why 认可的选择：本地单机场景，外键带来的约束成本高于收益。

**知识点录入与 AI 固化**。单条录入、录入查重、AI 结构化固化、批量固化、人工合并/拆分/修正、Word 导出。这里定下一条后来一直沿用的规矩：**六板块提示词一次发送、一次完整返回，软件不切割提示词、不分段调用再拼接**。AI 对不适用板块返回的「无此内容」类空话，由代码侧过滤。

**学情与选题**。0–5 级熟练度，满级停止复习；双模式遗忘曲线（按周 `2×(1+2^熟练度)` 天，按日 `0.4×(1+3^熟练度)` 天）；待复习候选池、人工选题、答题记录、学情统计。

**AI 出题与批改**。六大题型，按「会读 / 会写」分层抽题；题目实时生成、以 Word 输出，不入库、不固化、不复用；客观题本地比对，主观题 AI 批改，批改结果回写学情。

**前端与维护**。原生 HTML + CSS + JS，由 C++ 后端直接托管在 8088，没有独立前端服务；备份、学情重置、临时 Word 定时清理。

**AI 架构也换过三次**：最初是本地 LocalAI / Mock 规则引擎，离线零 Token；后来按需求改为在线调用，试过通义千问；最终定为智谱 GLM-4-Flash，经本地 Node 网关转发，完成 HTTP→HTTPS 与 Key 注入。Why 的取舍很明确：**免费、稳定、数据不出本机**。

这一版结束时 196 项测试。现在回看，它很粗糙，但接口、表结构和「本地数据 + 在线 AI」的边界都是这时候定下的。

## 二、v1.1.0：从「能用」到「像个产品」

Why 拿参考站 sura-tify 的设计要求复刻视觉，同时给了一条硬边界：**没有后端支撑的功能不许伪造**。所以文章页当时老老实实做成「即将推出」，而不是编一个假阅读器。这个决定后来救了很多次离线演示。

设计上从参照站实测设计令牌（配色、圆角、阴影、间距），引入 Fraunces（衬线标题）+ Karla（正文），4 个 woff2 字体文件全部下载到本地，不引 CDN；六个页面整体重建，后端补 `font/woff2` MIME。Why 对离线的坚持是：**可以多几个本地文件，不可以多一个外网依赖**。

这一版还修了一个会直接崩进程的问题：`libmysqlclient` 不是线程安全的，多线程共享同一个 `MYSQL*` 会堆损坏。修法是递归互斥锁 + `mysql_thread_init()` + 禁用 SSL。这个修复没有界面，但它让后端能连续跑住。

回归从 196 项增加到 205 项。

## 三、v1.2.0：多人使用，日常学习闭环

这是第一个「功能变厚」的版本，三件事都很重。

### 3.1 多用户认证（T004）

不是加一个登录框那么简单。新建 `users` + `user_sessions` 两表，保留 `user_id=1` 给游客；`auth.h` 用 CommonCrypto SHA-256 + `/dev/urandom` 生成 salt/token；`http_server.h` 增加前置回调，main.cpp 用 `thread_local` 保存当前用户；knowledge / wordbook / learning / maintenance 四个 Service 共 **15 处写死的 `user_id=1`** 改成请求上下文读取。

更麻烦的是数据边界：跨用户固化复用时，命中他人记录要在事务内复制全部子表，但不碰对方学情；批量取数、详情、Word 导出等 4 处 SQL 补上 `AND user_id=<ctx>`；注销账号要在事务内级联删干净，游客不可注销。前端新增登录/注册页和全局导航用户区，8 个页面统一接入。

Why 在这里的判断是：**复用「知识」可以，复用「学情」不行**。这条边界后来一直没破。

### 3.2 播放复习（T006）

后端只做了一件事：`GET /api/playback/queue` 按记忆状态返回复习队列。前端补公共 TTS 模块 `static/tts.js`（浏览器 Web Speech API），在知识点详情和单词本词条上加朗读按钮。**没有单独的播放复习页面**——这是当时收敛范围的结果，原计划里的 `playback.html` 并没有落地，文档后来已按实际情况修正。

### 3.3 每日小测（T007）

新建 `daily_quiz` + `user_coin` 两表。每次实时生成 **3+1+1** 五题：3 题来自已固化知识点、1 题熟词生义、1 题新知，全部客观题；本地秒批，不调 AI 批改；答错熟练度 −1（下限 0）、错误次数 +1，**不动 `next_review_time`**，避免小测干扰遗忘曲线；第 4/5 题可一键走现有固化管道，固化对象是「单词 + 目标义项」。词币当轮只预留 `coins_earned: 0`，没有真正读写。

AI 返回的健壮性也在这轮补了不少：兼容 `{"questions":[]}` 包装与裸数组、清洗 `A)`/`A.` 选项前缀、example 退化成挖空句时用答案词自愈、格式错误整卷拒绝不落库。

### 3.4 测试隔离：Why 发现的隐患

这轮收尾时 Why 点出一个严重问题：全量回归会清空 `knowledge_points`，把本机真实词条也删了。于是 stage2/3/4/5/6 与 e2e 六个套件统一改成「专用测试用户」：按 `t2user_`/`t3user_`/`t4user_`/`t5user_`/`t6user_`/`e2euser_` 前缀清理自己上次的数据，注册专属账号，后续请求带 Cookie，SQL 断言按 `user_id` 过滤。跑完核对：真实账号与词条零变化。

顺带修掉 `learning-center.html` 的 `limit=1000`——后端分页参数是 `size`，写错会静默返回默认条数。

回归从 285 项到 336 项（12 套件）。

## 四、v1.3.0：因人而异，内容变厚

### 4.1 提示词集中化与学习者身份（T001）

原来五套 AI 提示词的大段文字埋在 Service 代码里，改一处要翻几个文件。Why 要求抽出来。于是新建 `backend/include/prompts.h`，把单条固化、批量固化、出题、主观题批改、每日小测五套模板、共享段落、JSON Schema 全部收进 `namespace eng::prompts`，共享部分合并去重，编译期常量、零运行时开销。

同时加入「学习者身份」：`learner_identities` 字典表（初中生 → GRE 共 10 项）+ `users.learner_identity` 列；新增 `PUT /api/auth/profile`、`GET /api/learner-identities`，`GET /api/auth/me` 返回身份；5 处 AI 调用统一从 `prompts::getLearnerIdentity()` 读取，游客或查库失败回落到「高中生」。

Why 的判断很关键：**身份不是代码里的 if-else，而是一段交给模型理解的场景描述**。所以提示词里的占位符直接注入身份字符串，让模型自己理解该考什么、怎么讲，而不是在后端枚举映射。措辞可以从命令式改成建议式，但 JSON 格式、字段必填、选项约束这些机器解析硬依赖必须回紧——这条后来在 T014 又验证了一次。

### 4.2 文章模块阶段 1（T000）

新建 6 张文章表，`backend/data/efllex.tsv` 预置词频表，最终加载 **13,546 词条**；规则分句（45+ 缩写词表，不调 AI）；CEFR 难度分析；7 条文章 CRUD 路由（`/api/article/my` 必须排在 `/api/article/:id` 前面）。前端 `articles.html` 只做基础列表与录入，阅读功能没有假装实现。

这轮修了 4 个历史 bug：`splitTab` off-by-one 让词条从 10,140 变回 13,546；难度报告漏 `vocab_cefr`；AI 固化会润色词形，查重只比 `standard_content` 导致 Miss，补 `OR user_input_content`；`exercise_types` 从未赋值，补 AI JSON 提取 + 兜底。修完 12 套件 349 项全过。

### 4.3 点金圣殿（T005）

Why 想给学习行为一个长期激励。新建 4 张表（`user_coin_txn`/`user_seal`/`user_title`/`user_weekly_goal`）+ `config/rewards.json`，新增 `TreasuryService` 和 5 条 `/api/treasury` 路由：金桂主币、朱砂印×7、称谓×5、本周课规、收支流水。

上线时修了 3 个 bug：`isValidGoalType` 未判空直接取属性、幂等扣费预检查残留导致重复扣、非法 `goal_type` 未校验就写入。后来补了三联动：L5 词条固化后检查朱砂印与称谓，复习和小测完成后推进本周课规，全部幂等，不再新增接口。

界面上没有独立宝库页，宝库是嵌在仪表盘/全站导航里的抽屉——**文档已按这个实际情况修正**。这一版回归记录到 376 项（13 套件）。

## 五、v1.4.0：把精讲做成能读的东西

如果说 v1.3 是「加内容」，v1.4 就是「让内容真的能用」。五场硬仗，按时间顺序。

### 5.1 T001：固化完的词，详情页是白的

Why 的反馈很具体：「录入知识点，点固化，详情页没有显示」。我先复现，没有先改代码。正常词条能显示；同名词条触发合并后，再打开旧 id，页面全白，控制台却干净。问题不在接口，在详情页：它把 URL 里的 id 直接塞进下拉框，选中项落空，`loadDetail()` 提前返回。

修法是兜底：id 失效就显示最新词条并提示「已被合并」，列表为空给引导文案，录入页把合并目标 ID 显示出来。

紧接着第二个反馈更扎心：「录入 appopriate，固化的却是 venture」。这条真实数据比任何猜测都值钱——`venture` 的音标 `/ˈventʃər/` 正好是当时提示词 schema 里的示例值。模型把示例词当成了目标词，入库代码又完全信任 `standard_content`。

我先按词形做校验，全量回归立刻打脸：`benefit→beneficial`、测试合成词 `t002retryword→retry` 都被误判，5 个套件失败。后来改成包含关系，并补了两件计划外的事：错配时带纠正说明重试一次；批量数组与词表错位时逐条重试。还把单条 `max_tokens` 从 2048 提到 4096——多义词 JSON 被截断时，报错会伪装成「AI returned no JSON」，很容易被当成网络抖动。

这一场教我的事：**示例也是提示词，示例词会被模型当成答案**。同时把测试隔离补齐，新增 stage13 专项套件 20 项，回归到 437 项；Why 拍板版本保持 v1.4.0，不升 PATCH。

### 5.2 T010：讲解从十一个字段变成一整块 Markdown

原来的精讲散在十一个 extras 字段里，前端一条条拼 `<br>`。Why 要的是「像一篇能读的讲解」，不是数据库字段展览。

方案定得很死：结构化字段（definitions/collocations/synonyms/antonyms）继续走子表；音标、词根、同源词、典故、频率、语域、文化延伸等讲解内容合并成一条 `kp_extras(extra_type='markdown_content')`；旧数据继续按 `<br>` 渲染，不迁移、不丢。

前端没有引 CDN，而是把 marked v12.0.2 下载到 `frontend/static/marked.min.js`，配一层标签/属性白名单消毒。Why 的底线：**可以多一个文件，不可以多一个外网依赖；可以渲染 Markdown，不可以直接 innerHTML**。

实现时踩了两个坑：GLM 会把 Markdown 的真实换行写进 JSON 字符串，导致 JSON 非法；精讲变长后单条固化明显变慢。前者解法是把 `markdown_content` 定义成「字符串数组，一行一个元素」，入库前拼接，再加控制字符修复兜底；后者先收紧篇幅，后来在 T014 重新调平衡。

编码前的计划核对还翻出三处过期引用：`frontend/static/kp-detail.js` 早就不存在、测试入口是 `node tests/run_all.js`、`kp_extras.content` 是 TEXT 不是 MEDIUMTEXT。**先核对再动手**，省下了半天白工。回归 440 项。

### 5.3 T012：批量固化又慢又整批失败

Why 的原始判断是「调用 AI 次数太多」。我没顺着猜，先去量：真正的原因是单次响应被 `maxTokens` 截断——`1024 * min(N,4)` 封顶 4096，新 Markdown 每词约 450–600 token，7 词以上必截断，重试两次还是失败，于是又慢又没结果。

给了三个方案：A 分片并发、B 纯并发单条、C 异步任务。Why 选了「C 异步 + A 分片」，还加了两条硬要求：**生成中要能看见已完成的词**，**断网/重启后能续跑**。

于是有了 `solidify_jobs` / `solidify_job_items` 两张表、4 个任务接口、词条级渐进可见、启动时把遗留 `running` 置 `interrupted`、用户手动「继续」。分片后来稳定为 3 词，并发默认 3（可在 `config/ai.json` 调整，异常回落 2），超时 180 秒。

这一轮还抓到一个真缺陷：批量词表拼接从第二个词起，发给 AI 的是字面量 ` << kp <<`，不是真实单词。这很可能也是「单词本批量导入只有核心内容」的原因之一。

SSE 流式和不完整 JSON 容错被 Why 明确存档：「以后可能做，这期不做」。这句话让范围没有失控。回归 456 项。

### 5.4 T013：Word 里得看见公式，而不是 `\frac`

详情页的 Markdown 好看了，导出的 Word 还是旧格式。Why 的要求是：新格式词条导出也要有标题、粗体、列表、引用，LaTeX 要变成 Word 公式，旧格式词条不能坏，单个和批量都要覆盖。

我先比较了三条路：继续手写转换、`remark-docx`、`markdown-docx` + 适配层。Why 更看重「完整 Markdown 语法、不介意外加一个 npm 依赖」，又追问「以后可修改性更强」——最后拍板 `markdown-docx` + 适配层。

`remark-docx` 先被排除：0.3.29 用了 Node 22 的 Iterator Helpers，项目 Node 20.17 直接 `TypeError`；而且它返回整份 ArrayBuffer，塞不进现有的页脚、分页、多词结构。

`markdown-docx` 也不是一装就好。第一次导出只剩文档头，原因是 `docx` 两个版本共存；锁到 9.14.0 后内容回来了。第二次标题退化，因为段落引用了 `MdHeading2`，但 `styles.xml` 没注册；把转换器的 `paragraphStyles/characterStyles/numbering` 注入 `Document` 才正常。公式用 KaTeX 转 OMML，`\(...\)`/`\[...\]` 先归一化成 `$...$`/`$$...$$`，`<script>/<style>` 先整段删掉。

测试里加了 Word XML 断言：至少 3 个 `<m:oMath>`、有粗体、有列表编号、没有 `**`/`##`/`\frac`/`<script`、H1 不重复、新旧格式和批量都能并存。Why 后来用 Word/WPS 打开样本看过，这一项才算真正闭环。回归 471 项。

### 5.5 T014：精讲只剩「核心含义与例句」

Why 说：「部分单词的单词精讲仍然只有核心含义与例句一项」。

我先查数据库，再查 `ai_tasks` 的原始返回。结论很明确：前端没截断，Word 没截断，是 AI 真的只写了一节。40 个含 Markdown 的词条里，22 个只有一节。

根因不是模型笨，是提示词自相矛盾：一处写「最多 2 个二级标题」，另一处列了十余个维度；JSON 示例只给一节；备注规则又说「无关维度省略」。模型同时听了两句相反的话，随机偷懒。

修法不是一次到位，是 Why 一轮轮改提示词、我一轮轮编译实测：

- 先加 `venture` 的完整示例，按「音标/频率→核心释义→词根→同源词→搭配→同义辨析→补充」示范；
- 再禁「无固定搭配 / 暂无 / 不适用」，没内容就整节删；
- 再按水平调难度和英文占比，高中/高考英文≥50%，多给英文例句；
- 再要求不求齐全，2–6 个有价值维度，逻辑清楚、语言生动；
- 最后 Why 批准压缩方案 A–E，提示词从 8.3KB 降到约 5.9KB，同时把分片调到 3、并发调到 3、超时调到 180 秒。

实测单条从 23.6 秒降到 18 秒上下，3 词批量约 28 秒（压缩前 4 词要 118.6 秒）；测试等待窗口相应放宽：stage11 考后固化 30s→130s，stage2 异步轮询 160s→300s。T014 后全量回归 **14 套件 471 通过 / 2 跳过 / 0 失败**；此后多轮提示词人工修改，回归仍保持 14 套件全通过。

英文占比和每节例句数目前仍靠提示词约束，没有后端强制校验；旧词条不会自动按新提示词重写。这两条局限我如实写在这里。

## 五·补、v1.4.1：让开发者一条命令跑起来

这一版的题目不是加功能，是「交出去」。Why 的要求很具体：让开发者一条命令跑起来，让普通用户打开浏览器就能用，长期成本不超过 ¥99/年。阶段一是零成本的本地分发，阶段二才是云上站点。

**先拆掉三颗钉子**。第一颗是 macOS 专有依赖：`auth.h` 用 Apple 的 CommonCrypto 做 SHA-256，Linux 上没有，改成纯 C++ 实现。第二颗是 MySQL 8.0 的 `SSL_MODE_DISABLED` 在 MariaDB 客户端头文件里不存在，用 `LIBMYSQL_VERSION_ID` 条件编译兜住。第三颗是 GCC 不接受乱序的指定初始化器，`ai_client.h` 按结构声明顺序重排。这三处不改，Docker 里根本编译不过。

**镜像分两段**。builder 用 `node:20-slim` 装 `g++` 和 MySQL 头文件，直接调用项目自己的 `scripts/build_backend.sh` 编译；runtime 只带 Node 20 和运行库。国内拉 Docker Hub 经常卡死，所以基础镜像默认走 `docker.m.daocloud.io` 镜像加速器，并且可以通过 `--build-arg BASE_IMAGE=` 换回官方地址。实测 mysql:8.0 拉取 43 秒、node:20-slim 27 秒。

**compose 只做两件事**：起 `elf-db`（mysql:8.0 + healthcheck）和 `elf-app`，端口只绑 `127.0.0.1:8088`，数据进 `mysql_data` 卷。AI Key 不再依赖 `config/ai.json` 明文文件，改由 `.env` 的 `ZHIPU_API_KEY` 注入容器内网关；`.dockerignore` 明确排除 `config/ai.json`。这一段踩了三个坑：

- MySQL 官方镜像的 `root` 默认只允许 localhost，跨容器连必须加 `MYSQL_ROOT_HOST: "%"` 并补 `GRANT`；
- 容器里的 `mariadb-client` 默认 latin1，中文读出来是 `??`。我一度以为数据损坏，`HEX()` 一查发现存的是正确的 UTF-8，真正原因是客户端输出编码，shim 里加 `--default-character-set=utf8mb4` 后 stage2 从 3 项失败变成 65 项全过；
- 测试脚本里 48 处 `/Users/junwang` 硬编码。新增 `tests/_env.js` 统一收口（路径、端口都能用环境变量覆盖），再加 `tests/_mysql_tcp_shim.sh` 把 `--socket=` 改写成 TCP，容器内 17 个套件全部通过。

**AI 网关崩溃那次**，现象是容器反复重启、固化任务全部 interrupted。根因不在业务代码：`config/ai.example.json` 里 `api_key` 写的是中文说明，entrypoint 原样复制成 `config/ai.json`，Node 把中文拼进 `Authorization` 头触发 `ERR_INVALID_CHAR`，网关崩了，`restart: unless-stopped` 又把它拉起来，循环往复。修法三条：示例 Key 置空、网关启动前校验必须为 ASCII、启动时重置非法 Key。

**固化「卡住 377 秒」** 也量过：里面有容器崩溃期的中断，也有 AI 单次 26.5 秒的真实耗时（输入 6679B、输出 1937B，一次调用无重试）。Why 选了最小改动：前端加秒表反馈，不改提示词、不动后端流程。

**开发环境第一批**——为什么先做这个？因为「一条命令跑起来」的前提是开发者能自检。于是有了 `./dev`：`up`（容器）/ `up --host`（本机）/ `down` / `debug` / `logs` / `doctor` / `test`。`doctor` 会把编译器、Node、配置、AI Key、数据库、端口、Docker 逐项检查。它第一次运行就抓到了真问题：本机 `clang++` 根本不可用。

**clang++ 的真相**比预想严重：不是「标准库缺一部分」，而是 `/Library/Developer/CommandLineTools` **整个目录不存在**（系统升级后被清除）。`xcode-select --install` 能拉起安装器，但点「安装」后失败。查 `/var/log/install.log` 看到 `installation-check` 脚本报 `TypeError: null is not an object (evaluating 'cpuFeatures.split')`。根因是 `sysctl -n machdep.cpu.features` 在 Apple Silicon 上返回空值，Apple 这个版本的 CLT 安装包自己崩了。换成 `softwareupdate -i` 也一样，因为它跑的是同一个 distribution 检查。

绕法是绕开产品级检查：从 Apple 软件更新目录直接取 4 个**组件包**（`CLTools_Executables`、`CLTools_macOSNMOS_SDK`、`CLTools_macOSLMOS_SDK`、`CLTools_SwiftBackDeploy`），用 `installer -pkg` 逐个安装。装完 `xcode-select -p`、`clang++ --version`、`#include <string>`、`scripts/build_backend.sh` 全部通过，`./dev doctor` 全绿。

**宿主机回归**最后一块拼图：Docker 容器占着 8088，得先 `docker compose down`（不清卷）；本机 MySQL 起来后又被回收，原因是进程跟着启动命令的会话一起结束。解法是把「起 MySQL + 网关 + 后端 → 等就绪 → 跑 17 套件 → 收尾停止」放进同一条命令，全程存活。宿主机最终 **17 套件 544 项通过 / 2 跳过 / 0 失败**，与容器内结果一致。
