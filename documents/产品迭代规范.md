# 产品迭代规范

> 文档版本：v1.1.0
> 创建日期：2026-09-25
> 更新日期：2026-09-26
> 适用范围：本项目（轻量化本地英语学习软件）所有需求迭代、版本发布、代码与数据库变更。
> 本文档为项目长期规范，所有开发活动必须遵循；变更需更新文末变更记录。

---

## 一、总则

1. 每个需求（任务）遵循统一流程：**先计划、后开发、必回归、同步文档**。
2. AI 仅在规定边界内使用，但在不涉及安全问题时，不对AI进行硬性约束（见第六章）。
3. 所有结论必须基于真实代码与测试结果，禁止伪造功能、接口与数据。
4. 参照第三方产品改编时，须确认已取得合法授权并在任务文档中注明。
5. 所有不明确的问题向我咨询。
6. 尽量参考网上已有示例完成内容。
7. 若目标功能已有成熟软件 / 网站方案，且支持本地集成接入，则优先采用该现有方案，**不重复从零开发实现**。
8. 注意：你是软件开发者，而不是软件接入的AI。
9. 当不同文档存在冲突时，向我咨询，并修正错误文档。
10. **每项功能都提供人工修改渠道**。
11. 应按照开发计划逐步开发，每轮对话只完成一个任务。

## 二、代码风格规范


### 2.1 通用原则

- **可读性优先**：代码是给人读的，其次才是给机器执行；命名清晰优于简短。尽量减少代码行数，意义明确且实现同一功能的代码可压缩至同一行
- **一致性优先**：与既有代码风格保持一致，不引入混合格式。
- **最小化依赖**：不引入需求外的三方库；优先使用语言标准库。

### 2.2 C++ 后端规范

- 大括号风格：在不改变原有代码的基础上改用 Allman 风格，左侧大括号换行（除非左右大括号在同一行）
  ```cpp
  if (condition)
  {
      do_something();
  }
  ```
- 命名约定：类名 PascalCase，函数/变量 camel_case，常量 UPPER_SNAKE_CASE，私有成员以下划线结尾
- 头文件保护：使用 `#pragma once`，不使用 `#ifndef` guard
- 包含顺序：系统头文件 → 第三方头文件 → 本项目头文件，每类之间空一行
- 禁用全局变量：使用单例或依赖注入替代
- 异常处理：关键路径使用 try-catch 捕获，不吞异常；错误信息经 `Db::escape()` 转义后输出

### 2.3 JavaScript / Node.js 规范

- 使用 `const` / `let`，禁用 `var`
- 异步代码使用 `async/await`，不嵌套回调
- 错误处理：每个 async 函数末尾有 try-catch，错误统一 return `{ ok: false, msg: '...' }`
- 测试文件：每个测试套件顶部定义 `pass` / `fail` / `skipped` 计数器，输出格式统一为 `✓` / `✗` / `~`

### 2.4 HTML / CSS 规范

- 页面结构：使用语义化标签（`<header>`, `<nav>`, `<main>`, `<section>`, `<footer>`）
- 样式集中：所有设计令牌（颜色、圆角、阴影、间距）定义在 `frontend/static/style.css` 的 `:root` 中，页面内不散落魔法值
- 字体本地化：所有字体 woff2 文件存放于 `frontend/static/fonts/`，通过 `@font-face` 加载，保证离线可用
- 禁止行内样式：不使用 `style="..."` 属性

## 三、迭代流程

```
需求确认 → 影响面分析 → 编写开发计划 → 开发实现 → 自测 → 全量回归
    → 用户测试 → 文档同步与变更记录 → 版本号升级 → 发布/交付
```

| 环节 | 要求 |
|------|------|
| 需求确认 | 明确事实源（如《主要问题.docx》）；需求歧义先澄清，不臆测 |
| 计划先行 | 未形成开发计划与验收标准前，不开始编码（用户明确豁免的除外） |
| 开发实现 | 严格限定在影响面清单内；路由文件在中间件类重构中不得擅改；不引入需求外的改动 |
| 自测 | 先验证受影响功能闭环；涉及并发须做并发验证（串行 curl 无法暴露竞态） |
| 全量回归 | 测试套件全部运行，全部通过方可发布；AI 相关失败需区分网络抖动与代码缺陷并重跑确认 |
| 用户测试 | 停止对话，说明测试方式，让我检查功能是否符合要求。 |
| 文档同步 | 更新《工作总结》《后续计划》及受影响的架构/规范文档，追加变更记录 |
| 版本升级 | 按《编号规范》判定升哪位号，并同步全部登记位置 |

## 四、数据库与接口变更规范

### 4.1 数据库

- 变更 SQL 统一存放 `scripts/sql/`，文件名按序号编号并具描述性；
- **加表/加列视为兼容变更**（MINOR）；正式版本完成后，删表/删列/改列语义原则上禁止，确需则属 MAJOR 并须提供数据迁移方案；
- 每次结构变更前后各做一次数据库备份（`backups/`）；
- 继续遵循现有约定：InnoDB、utf8mb4、**不设外键**，关联一致性由 Service 层保证；所有删除操作须做子表级联清理。

### 4.2 HTTP 接口

- 路由统一在 `backend/src/main.cpp` 注册；命名使用名词复数、kebab-case 多词连写；
- 新增接口 = MINOR；**删除、改名或改变既有响应结构 = MAJOR**；
- 客观题批改由代码完成，主观题批改由 AI 完成，规则不混淆；
- 面向未来如需多版本共存，使用 `/api/v2/...` 路径前缀（当前 `/api/...` 视为 v1）。

### 4.3 前端

- 保持原生 HTML + CSS + JS、由后端托管、无独立前端服务的现状；
- 颜色、字体、圆角、阴影等设计令牌集中在 `frontend/static/style.css`，页面内不散落魔法值；
- 字体等静态资源本地化，保证离线可用；静态托管须配置正确 MIME。

## 五、AI 使用边界

1. 遇到安全问题时，必须向我询问。
2. 提示词整段一次发送：用户写好的完整提示词须原样构造为一次请求，禁止软件切割提示词、分段调用再拼接答案。
3. 临时 Word 文件由定时任务自动清理。
4. AI 对不适用的内容项应留空/省略，代码侧做空话过滤（"no/none/无"类）。
5. AI 返回内容中的关键判定（如"会读/会写"掌握要求）以代码规则为准，不盲信 AI。
6. AI 模型与网关配置变更须在任务文档中记录原因与兼容性结论。
7. 对于非安全问题，尽量不给 AI 加强制性约束。

## 六、文档体系与更新要求

| 文档 | 职责 |
|------|------|
| 《产品需求文档》 | 产品定位、功能需求 |
| 《程序架构说明》（docx） | 架构、进程、模块、接口；架构变更后刷新 |
| 《工作总结》 | 已完成工作、已核实功能、不足、修正方案 |
| 《后续计划》 | 尚未启动的开发任务、优先级与版本规划 |
| 《编号规范》 | 版本编号与任务编号规则 |
| 《开发经验总结》 | 开发中遇到的问题、根因与解决方案 |
| `documents/{版本号}-{任务描述}/开发计划.md` | 单次迭代的计划与完成记录，任务确认完工后保留（作为历史记录） |

通用要求：

- 每份规范/总结类文档维护各自的**变更记录**（日期、版本、摘要、原因）；
- 优先修改既有文档，不重复创建同主题文件；
- 文档中的文件路径、接口、函数名必须与代码一致；
- 任务编号统一使用 `v{版本}-T{序号}` 格式，如 `v1.1.0-T001`。

## 七、发布检查清单

发布前逐项确认：

- [ ] 7 个测试套件全部通过（记录各套件通过数）；
- [ ] 受影响页面在浏览器中完成功能闭环验证；
- [ ] 涉及并发/稳定性的改动通过并发压测；
- [ ] 数据库变更有备份、有编号 SQL；
- [ ] `config/app.json` 版本号已升级；
- [ ] 《工作总结》《后续计划》及相关文档已更新并追加变更记录；
- [ ] 任务计划的"完成记录"已填写，遗留事项已列明；
- [ ] 三服务（MySQL、AI 网关、后端）可用，一键启动/停止脚本未被破坏。
