# 团队合作版 · 改造分析清单

> 版本：draft-v0.1 | 创建：2026-10-04
> 本文件为**内部技术评估**，记录从单用户版转向团队合作版所需的所有改造项，含可行性分析与建议决策。
> 不与 GitHub 同步。

---

## 一、现有架构瓶颈（为何不能直接加 team 功能）

| 瓶颈 | 现状 | 影响 |
|------|------|------|
| DB 单进程单连接 | `Db` 类使用单个 `MYSQL*` + 递归锁串行化，仅适用于本机单用户场景 | 多客户端并发时成为瓶颈；远程部署时需改造为连接池 |
| 数据隔离靠 user_id 硬编码 | 所有业务查询均拼 `AND user_id=?`，**无表级权限概念** | 加 team 需大改 Service 层每一处 SQL |
| HTTP 服务器手写，扩展性差 | Crow 源码内嵌于 `http_server.h`，仅支持 GET/POST/PUT/DELETE 基础路由，无中间件链、无 WebSocket | 实时协作（教师推送通知、多人共编文章）无法实现 |
| 前端无状态架构 | `nav.js` 通过 `fetch('/api/auth/me')` 每次请求身份，无全局状态管理 | 团队切换需刷新整个页面，体验差 |
| AI 网关单 Key | `local_ai_server.js` 全局共享一把 API Key，无租户隔离 | 多团队共用 Key 无配额管控，成本不可控 |
| 部署绑定本机路径 | 硬编码 `/Users/junwang/.local/...` 等路径于 `start_mysql.sh` 与 `main.cpp` | 他人部署需大量手工修改 |

## 二、分模块改造清单

### 2.1 后端语言与框架

| 项 | 现状 | 改造方案 | 优先级 | 工作量 | 建议 |
|----|------|---------|-------|--------|------|
| 后端运行时语言 | C++17 + 手写 HTTP 服务器 | **建议暂不改**；C++ 性能好且当前规模够用，改用其他语言代价高 | 低 | 大 | 若确实需要，推荐 Rust（性能相近，有 Actix/axum 成熟生态）或 Go（Gin/Echo） |
| HTTP 框架 | 内嵌 Crow 源码 | **建议替换为独立依赖**：Nginx 反向代理 + 后端只做 API；或直接换框架 | 中 | 中 | 短期可保持现状，先加路由前缀 `/api/team/*` 即可 |
| 并发模型 | 每连接一线程（thread-per-connection） | **必须改造**为异步 I/O（epoll/io_uring）或使用 EventLoop，否则 50 人以上并发连接数将耗尽资源 | 高 | 大 | 若换 Go/Node.js 后端可自然解决；C++ 侧可用 Boost.Asio 改造 |
| 会话存储 | 内存 token + MySQL sessions 表 | 保留 MySQL sessions 表；增加 Redis 作会话缓存（可选） | 低 | 小 | |

### 2.2 数据库

| 项 | 现状 | 改造方案 | 优先级 | 工作量 |
|----|------|---------|-------|--------|
| 单库单实例 | 本地 MySQL 8.0 | 若团队规模 >50 人，考虑 MySQL 主从或迁移到 PostgreSQL（JSON 支持更好） | 低 | 中 |
| 无连接池 | Db 类持有单个 MYSQL* | 改为连接池（如 mysqlxx 或 PooledConnection） | 高 | 中 |
| 索引不足 | 现有索引仅 user_id/knowledge_id | 新增 `idx_team_id`、`idx_role`、联合索引（team_id + user_id）等 | 高 | 小 |
| 无事务隔离级别控制 | 默认 REPEATABLE-READ | 明确设置 READ-COMMITTED，避免共享资源并发冲突 | 中 | 小 |

### 2.3 认证与授权

| 项 | 现状 | 改造方案 | 优先级 |
|----|------|---------|-------|
| Cookie 鉴权（HttpOnly） | 已有，安全 | 保持不变；增加 JWT 作为额外鉴权手段（可选，便于 API 直调） | 中 |
| 无密码强度校验 | 仅长度 ≥6 | 增加复杂度要求（大小写+数字），对接 bcrypt/argon2（当前 SHA-256 不够强） | 高 |
| 无登录限流 | 无 | 增加 IP 级别登录频率限制（如 5 次/分钟） | 高 |
| 无二次验证 | 无 | 增加 TOTP（Google Authenticator）作为可选二步验证 | 低 |
| 游客账号 id=1 永久保留 | 硬编码 | 移除游客机制，所有人强制登录（团队版常见做法） | 中 |

### 2.4 前端

| 项 | 现状 | 改造方案 | 优先级 |
|----|------|---------|-------|
| 原生 HTML/JS，无框架 | 全部页面硬编码 | **建议评估迁移到 Vue 3 或 Svelte**：组件化后团队管理页开发效率提升 3-5 倍；维护成本也更高 | 高（可选） |
| 无状态管理 | nav.js 独立 fetch 身份信息 | 引入 Pinia（Vue）或 Zustand（Svelte）做全局状态，避免重复请求 | 中 |
| 前端与后端耦合 | 后端托管静态文件 | 解耦：前端独立构建后推 CDN/S3，后端只提供纯 API（JWT） | 中 |
| 无 PWA 支持 | 无 Service Worker | 增加 PWA manifest 与 Service Worker，支持离线缓存（学习场景有价值） | 低 |
| 页面间路由 | 纯链接跳转 | 改用前端路由（Vue Router / Path-to-Regex），单页应用减少刷新 | 中 |

### 2.5 实时协作功能

| 功能 | 现状 | 所需技术 | 优先级 |
|------|------|---------|--------|
| 教师推送公告/作业通知 | 无 | WebSocket（集成 libwebsockets 或换 Node.js 子服务） | 高 |
| 多人共编文章/笔记 | 无 | CRDT 或 Operational Transform（如 Yjs） | 低（远期） |
| 团队聊天/讨论区 | 无 | 轻量级 WebSocket 聊天室 | 中 |
| 学习进度实时同步 | 无 | Server-Sent Events（SSE）比 WebSocket 更简单，适合单向推送 | 高 |

### 2.6 AI 网关

| 项 | 现状 | 改造方案 | 优先级 |
|----|------|---------|-------|
| 单 Key 全局共享 | `config/ai.json` 一把 key | 改为**按 team 分配 Key**（各团队独立密钥），或增加配额限制（如每月 N 次调用） | 高 |
| 无调用审计 | ai_tasks 无 team 维度 | 加 `team_id`、`user_id`、`cost_token_estimate` 列 | 中 |
| 无模型降级策略 | 超时即失败 | 增加备用模型 fallback（如 glm-4-flash → glm-4-flashx） | 低 |

### 2.7 部署与运维

| 项 | 现状 | 改造方案 | 优先级 |
|----|------|---------|-------|
| 路径硬编码 | `start_mysql.sh`、`main.cpp` 写死 `/Users/junwang/.local/...` | 提取为环境变量或统一 `config/env.json`，支持 Docker 化部署 | 高 |
| 无 Docker 支持 | 无 | 编写 `Dockerfile`（C++ 编译镜像）+ `docker-compose.yml`（MySQL + 后端 + 网关） | 高 |
| 无 CI/CD | 手动编译 | 增加 GitHub Actions：push 后自动编译 C++ 并运行测试套件 | 中 |
| 无监控 | 无 | 增加健康检查端点 `/api/health`（已有）+ Prometheus metrics 暴露（可选） | 低 |

### 2.8 安全加固

| 项 | 现状 | 风险等级 | 改造方案 |
|----|------|---------|---------|
| SQL 注入防护 | `Db::escape()` 手动拼接，有遗漏风险 | 高 | 全面改用预编译语句（PreparedStatement）或 ORM |
| CORS 全开放 | 无 Origin 校验 | 中 | 增加白名单机制，仅允许已配置域名 |
| XSS 防护 | 前端部分有 `escapeHtml()`，非全覆盖 | 中 | 引入 CSP 头部；前端统一转义库 |
| 敏感文件泄露 | `.gitignore` 已修复，但需定期扫描 | 中 | 加入 `gitleaks` 或 `truffleHog` CI 扫描 |
| 密码存储 | SHA-256(salt+password)，无迭代 | 高 | 迁移至 bcrypt 或 argon2id |

## 四、是否值得改后端语言

| 对比维度 | C++（现状） | Go（推荐替代） | Rust（次选） | Node.js（仅做网关扩展） |
|---------|------------|---------------|-------------|----------------------|
| 开发效率 | 低（手动内存管理、编译慢） | 高（简洁语法、Goroutine） | 低（借用系统严格） | 高（同前端栈） |
| 并发能力 | 弱（每连接线程，锁竞争） | 极强（原生协程） | 强（async/await） | 强（事件循环） |
| 部署体积 | 大（需链接 mysql lib） | 小（静态编译） | 中 | 小 |
| 生态成熟度（HTTP+DB） | 一般（需自己拼） | 成熟（Gin+Gorm） | 成熟（Actix+SQLx） | 最成熟（Express/Nest） |
| 学习曲线 | 陡 | 平缓 | 陡 | 平缓（团队已熟悉） |
| 与现有代码兼容性 | — | 需重写全部后端 | 需重写全部后端 | 需重写全部后端 |

**结论**：
- 若团队人数 **< 30**，C++ 继续可用，**不建议换语言**，优先做连接池和部署标准化。
- 若团队人数 **≥ 50** 或需要实时协作，**推荐换成 Go**：开发效率最高、并发能力足够、代码量可减少 40% 以上。
- 若追求极致性能和内存安全且团队有 Rust 经验，可选 Rust。

## 五、最低可行团队版路径（MVP）

如果目标是"最快上线可多人使用的团队版"，建议只做以下 5 件事：

1. **数据库加 team 字段**：5 张业务表加 `team_id` 列，所有查询加 `AND team_id=?`（3 天）
2. **后端加路由**：`/api/team/*` 共 9 个接口，复用现有 AuthService 模式（5 天）
3. **前端加团队切换**：nav.js 加下拉选择器，调用 `/api/team/switch`（3 天）
4. **部署配置化**：把 `start_mysql.sh` 和 `main.cpp` 里的路径全部改为环境变量（2 天）
5. **测试新增 stage13**：覆盖团队 CRUD 和基本权限拦截（2 天）

**合计约 15 人天**，不换语言、不拆前端，即可上线基础团队功能。
