## 二、根因分析

### Bug 1（主因）：前端分页参数名与后端不匹配

**位置**：
- 前端：`frontend/pages/kp-entry.html:104`、`frontend/pages/kp-detail.html:75`
- 后端：`backend/src/main.cpp:91-96`（`handleKpList`）

**问题**：

```js
// 前端（错误）
const r = await fetch('/api/kp?limit=1000', ...);
```

```cpp
// 后端（只读 size，不认 limit）
int page = 1, size = 20;
try { page = std::stoi(req.queryParam("page").empty() ? "1" : req.queryParam("page")); } catch(...) {}
try { size = std::stoi(req.queryParam("size").empty() ? "20" : req.queryParam("size")); } catch(...) {}
```

前端传 `limit=1000`，后端忽略该参数，`size` 默认 `20`，只返回前 20 条。

**影响链路**：
1. 用户录入新词条 → 固化 → 刷新列表 → `load()` 调用 `/api/kp?limit=1000` → 实际只返回 20 条 → 若列表已有 ≥20 条，新词条排在第 21 位及以后，**不可见**
2. 知识点详情页 `initList()` 同样调用 `/api/kp?limit=1000` → 下拉列表只有前 20 条 → 新词条不在选项中 → **无法选中查看详情**

### Bug 2（次因）：合并删除导致词条 ID 失效

**位置**：`backend/include/knowledge_service.h:347-354`（`applySolidify`）

```cpp
if (!dup.empty() && std::stoi(dup[0]["user_id"]) == RequestContext::currentUserId())
{
    // 自己已有同名固化副本：合并
    db_.exec("DELETE FROM knowledge_points WHERE id=" + std::to_string(id));
    err = "merged into kp#" + dup[0]["id"];
    return true;
}
```

当新词条内容与已有词条完全相同（同 user_id），AI 固化时触发合并逻辑：**新词条被 DELETE**，返回原词条 ID。

**影响链路**：
- 固化成功后，前端仍持有原 ID（已被删除），跳转到 `/pages/kp-detail.html?id=42`
- `detail(42)` 查无此记录 → 返回 404 → 前端显示「加载失败」
- 列表中该 ID 也不复存在 → 「词条消失」

### Bug 3（辅助）：exportWord 硬编码 macOS 路径

**位置**：`backend/include/knowledge_service.h:503-504`

```cpp
std::string scriptPath = "/Users/junwang/Desktop/王浩源/英语/英语学习应用/scripts/gen_word_kp.js";
std::string cmd = "/Users/junwang/.local/bin/node " + scriptPath + ...
```

Windows 环境必然失败，与截图 2、5、8（导出 Word 报错 / 朗读失效）同源。
`root` 变量已在 `main.cpp:1100` 定义，可传入 `KnowledgeService` 或从 `root` 派生。

### 补充修复：详情页空白（2026-10-25）

**复现**：新建与已有固化词条同名的词条并固化 → 触发合并，新词条 ID 被删除；此时打开 `/pages/kp-detail.html?id={已删除ID}`，`sel.value = preset` 使选中项为空，`loadDetail()` 因 `id` 为空直接 return，`#detail` 完全空白且无任何提示。

**修复**

- `frontend/pages/kp-detail.html` `initList()`：先判断 URL 中的 id 是否存在于列表；存在才选中。若不存在或列表为空，回退显示最新词条并提示“词条 #X 不存在或已被合并，已显示最新词条”；列表为空时提示“暂无知识点”。
- `frontend/pages/kp-entry.html` `solidifyOne()`：读取响应中的 `j.id`（合并后的有效 ID），与点击时的 id 不同则提示“固化成功，已合并到已有词条 #X”。

**验证**

- 浏览器硬刷新后：`id=1156`（已删除）→ 详情页显示最新词条 + 合并提示；录入页对重复词固化 → 提示合并到 #1155，待固化的新行消失。

### 补充修复：固化内容错配为其他单词（2026-10-25）

**现象**：录入单词固化后，固化内容（standard_content、释义、例句）属于另一个单词。

**根因**：固化提示词的 JSON schema 用真实单词作示例值（`"phonetic":"音标如/ˈventʃər/"`，为 venture 的音标），GLM-4-Flash 会把示例词当目标词；批量固化时还会出现数组元素与词表错位，导致 abandon 被写成 "be done with"、benefit 写成 "be keen on"。入库代码完全信任 AI 返回的 `standard_content`，错误内容被永久写入。

**修复**

- `backend/include/prompts.h`：移除 schema 中的示例音标 `/ˈventʃər/`，改为字段说明；`KP_RULES` 增加“standard_content 必须是目标词本身，禁止替换为其他单词或近义词”。
- `backend/include/prompts.h`：`KP_SOLIDIFY_ONE_USER` 在“只输出 JSON”前新增 `{EXTRA_NOTE}` 占位符，供错配纠正重试插入说明（避免追加在收尾指令之后导致模型输出游离文字）。
- `backend/include/knowledge_service.h`：新增 `sameWordForm()`，允许拼写纠正/词形变化/包含关系（appopriate→appropriate、benefit→beneficial、t002retryword→retry），拒绝无关词（appropriate→venture、abandon→be done with）；`applySolidify` 在写入前校验，不匹配则拒绝入库并返回 `AI content mismatch`。
- `backend/include/knowledge_service.h`：`solidifyOne` 内容错配时带纠正说明重试一次，JSON 解析失败也重试一次；单条 AI 调用 `max_tokens` 由 2048 提到 4096（长 JSON 被截断会出现 `AI returned no JSON` / `JSON parse failed`）。
- `backend/include/knowledge_service.h`：`solidifyBatch` 对错位元素改走 `solidifyOne` 单条重试，不再把错位内容写入。

**验证**

- `appropriate` / `appopriate` 固化 → 内容均为 appropriate（拼写纠正后合并到已有词条）。
- 批量固化 abandon / benefit / comprehend → 三者内容均正确，无短语串位。
- 全量回归 14/14 套件通过（详见下方回归记录）。
