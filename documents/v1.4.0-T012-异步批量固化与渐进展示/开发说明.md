# v1.4.0-T012：异步批量固化与渐进展示 — 开发说明

> 状态：✅ 已开发并完成自测（2026-10-25）
> 关联：T010（知识点固化 Markdown 重构）
> 前置问题：词多时 `/api/kp/solidify` 单次批量响应超过 4096 token 被截断，重试 2 次后整批失败，表现为“很慢且无结果”

## 已确认决策

| 项 | 决策 |
|---|---|
| 架构 | C（异步任务 + 进度轮询） + A（分片 + 有限并发） |
| 并发 | **默认 2 路，可配置**（`config/ai.json` 的 `max_concurrency`），换模型时可直接调整 |
| 渐进可见 | **词条级**：一个词完成即入库可见，不做单词内逐字流式 |
| 任务记录 | **持久化**：支持任务历史、断点续跑，应对断网/重启 |
| SSE + 不完整 JSON | 仅存档为后续方向，本期不做（见第十一章） |

## 一、目标

1. 批量固化改为异步：提交后立即返回任务 ID，不再让前端长时间转圈。
2. 分片（每片 ≤4 词）+ 默认 2 路并发，消除“整批超 token 上限被截断”的失败；并发数可配置。
3. 已完成的词条立即入库并展示，用户不必等全部生成完。
4. 任务与每个词的处理状态持久化：断网、AI 失败、服务重启后，可查看历史并从断点继续，已完成词条不重复生成。

## 二、范围

**本期做**

- 异步提交、进度查询、任务历史、断点续跑四个接口
- 新增任务表与任务明细表（schema 变更）
- 分片（≤4 词/片）+ 并发（默认 2 路，配置可调）
- 词条级渐进可见
- 前端进度条、“已生成”列表、失败原因、历史任务与“继续”按钮

## 三、总体流程

```
前端点击“批量固化”
      │ POST /api/kp/solidify/async
      ▼
后端快照全部未固化词 → 写 solidify_jobs + solidify_job_items
      │ 立即返回 {job_id,total,status}
      ▼
后台 Runner：取 pending 明细 → 分片（≤4 词）→ 按配置并发（默认 2）调用 AI
      │                         │
      │                         ├─ 成功：逐词 applySolidify（事务）→ 立即入库、明细置 done
      │                         └─ 失败：明细置 failed，记录原因，不阻断其他片
      ▼
前端每 1.5s 轮询 GET /api/kp/solidify/jobs/:id
      │ 出现新 done id → 拉详情 → 立即渲染“已生成”
      ▼
全部明细处理完 → done / partial（有失败）

服务重启：running → interrupted；用户点“继续” → failed/pending 重新入队，done 不重跑
```

## 四、后端设计

### 4.1 数据模型（新增，迁移脚本 `scripts/sql/09_solidify_jobs.sql`）

```sql
CREATE TABLE IF NOT EXISTS solidify_jobs (
  id VARCHAR(32) NOT NULL,
  user_id INT NOT NULL,
  total INT NOT NULL DEFAULT 0,
  done INT NOT NULL DEFAULT 0,       -- 成功入库数
  failed INT NOT NULL DEFAULT 0,
  status VARCHAR(20) NOT NULL DEFAULT 'pending', -- pending/running/done/partial/failed/interrupted
  error TEXT,
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_user_status (user_id, status),
  KEY idx_update (update_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS solidify_job_items (
  id BIGINT NOT NULL AUTO_INCREMENT,
  job_id VARCHAR(32) NOT NULL,
  knowledge_id INT NOT NULL,
  status VARCHAR(20) NOT NULL DEFAULT 'pending', -- pending/running/done/failed/skipped
  error_msg TEXT,
  update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_job_kp (job_id, knowledge_id),
  KEY idx_job_status (job_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

- 新增表属新增功能；本任务归属 v1.4.0 迭代，发布时按 `skills/06-部署.md` 统一判定版本号，本任务不自行升号。
- 脚本使用 `CREATE TABLE IF NOT EXISTS`，可重复执行。
- 进度 = `(done + failed) / total`；历史查询只返回当前 `user_id` 的任务。

### 4.2 任务状态机

```
pending → running → done（全部成功）
                  ├→ partial（部分失败，可继续）
                  ├→ failed（全部失败，可继续）
                  └→ interrupted（进程重启，可继续）

interrupted / partial / failed --resume--> running
```

明细状态：`pending → running → done | failed | skipped`。
`skipped` 表示该词已固化（手工固化、跨用户缓存命中、重复合并），不重复调用 AI。

### 4.3 分片与并发

- 片大小 `solidify_chunk_size=4`；并发读取 `config/ai.json` 的 `max_concurrency`，默认 2。
- 并发数在启动时读取：取整后限制在 1–16；缺失、非数字或 <1 时回落 2；>16 按 16 处理。
- Runner 从 `solidify_job_items` 取 `pending`，组装片；按并发数创建等量工作线程消费片队列。
- 每片复用现有批量逻辑（从 `solidifyBatch` 抽出 `solidifyChunk(ids, uid)`），保留：
  - 跨用户缓存分流（命中零 AI，明细记 `skipped`）
  - `sameWordForm` 内容错配校验
  - 片内重试 1 次、失败原因写入明细
- `maxTokens` 按片内词数计算（4 词 ≈ 2400 token，留余量 4096），不再用 `1024 * min(N,4)` 对全批封顶。
- 工作线程必须为每个执行单元注入 `RequestContext` 用户身份（与中间件同一机制），否则会串用户。
- 每个词 `applySolidify` 内部已是独立事务：成功即提交，保证“生成完一个就能看到一个”。

### 4.4 断点续跑与幂等

- **启动恢复**：服务启动时执行
  - `UPDATE solidify_jobs SET status='interrupted' WHERE status IN ('pending','running')`
  - `UPDATE solidify_job_items SET status='pending' WHERE status='running'`
  不自动重跑，避免断网时无休止重试；由用户点“继续”。
- **继续接口**：仅任务所有者、仅 `interrupted|partial|failed` 可继续：
  - `failed` 明细重置为 `pending`；`failed=0`；任务置 `running`；启动 Runner。
  - `done/skipped` 明细不动，绝不重复调用 AI。
  - 任务已 `running` 或 `done` → 409。
- **断网**：AI 调用失败只把该片明细置 `failed`，任务继续跑其他片；网络恢复后点“继续”只重试失败项。
- **重复提交**：当前用户已有 `running` 任务时，返回该任务并标记 `reused=true`。
- **防双 Runner**：内存 `running_guard` + 状态条件更新（`UPDATE ... WHERE status IN (...)` 判断 affected_rows）双保险。

### 4.5 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/kp/solidify/async` | 提交全部未固化词；返回 `{job_id,total,status,reused}` |
| GET | `/api/kp/solidify/jobs/:job_id` | 进度与明细摘要（仅所有者） |
| GET | `/api/kp/solidify/jobs?limit=20&offset=0` | 当前用户任务历史 |
| POST | `/api/kp/solidify/jobs/:job_id/resume` | 从断点继续 |
| POST | `/api/kp/solidify` | 保留原同步接口，兼容旧前端/测试 |

### 4.6 配置与并发修改渠道

`config/ai.json` 新增（同步补入 `config/ai.example.json`）：

```json
"max_concurrency": 2
```

- 放在 AI 配置而非应用配置：换模型/换供应商时只需改 `config/ai.json`，与 `chat_model`、`base_url` 一起调整。
- 修改方式：编辑 `"max_concurrency"` → 重启后端生效（AI 配置在启动时加载，本期不做热更新）。
- 生效范围：本期仅用于固化分片并发；后续其他 AI 批量任务可直接复用同一配置项。
- 保护规则：1–16，异常值回落 2；这是防止误填导致线程暴涨的兜底，不限制正常调整。
- 实现后把 `config/ai.json` 登记到 `documents/devlog/人工修改渠道集合.md`。

`config/app.json` 不新增配置；片大小固定为 `solidify_job.h` 中的 `CHUNK_SIZE = 4`（标注 `[FUNCTIONAL]`），并发数才是换模型时需要调整的项。

`max_concurrent_ai_tasks` 当前未被代码读取，不复用，避免影响其他 AI 功能。

### 4.7 清理与保留

- 保留最近 30 天的已结束任务（`done/partial/failed/interrupted`）。
- 实际实现：`cleanupExpired()` 在服务启动和每次新建任务时执行，删除过期 `solidify_jobs` 及其 `solidify_job_items`；`running/pending` 任务永不清理。
- 本轮未新增独立定时器，避免引入额外线程；任务创建频率低，清理开销可忽略。

## 五、前端设计

仅改 `frontend/pages/kp-entry.html`，其他页面不动。

1. 点击批量固化 → 调 `/api/kp/solidify/async`，显示进度面板。
2. 每 1.5s 轮询任务接口；按 `progress/done/total` 更新进度条。
3. `completed_ids` 出现新 ID → 直接使用已加载的知识点列表生成“✓ 单词”链接，点击进入详情；不额外逐条请求详情。
4. `status=partial/failed/interrupted` → 显示失败词与原因，提供“继续”按钮。
5. 页面加载时调任务历史接口 `limit=10`：
   - 有 `running/pending` 任务 → 自动恢复轮询；
   - 有 `interrupted/partial/failed` → 显示“继续”入口；
   - 本期不渲染完整历史列表，历史查询接口保留给后续页面使用。
6. 浏览器断网/关闭后重进：任务仍在后台运行，历史接口可恢复进度；已完成词条始终可见。
7. `done` 后刷新知识点列表；轮询 404 时提示任务失效并回退列表。

## 十一、存档：后续可选方向（本期不做）

**SSE 流式 + 不完整 JSON 容错**

- 内容：单个词的 Markdown 边生成边推送（SSE），前端在 JSON 未闭合时容错抽取已生成的 `markdown_content` 片段并渐进渲染。
- 价值：把“词条级可见”提升为“单词内逐字可见”，首字延迟最低。
- 前置条件：
  1. 本地 AI 网关 5340 确认支持 `stream=true` 并能稳定透传；
  2. 需要容错解析半截 JSON（字符串未闭合、转义未完成）；
  3. 需要取消/断线重连机制；
  4. 前端需处理半截 Markdown 的渲染与安全消毒。
- 结论：复杂度和风险明显高于本期，作为未来方向存档，不进入 T012 范围。
