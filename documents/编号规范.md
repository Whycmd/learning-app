## 一、软件版本编号规范

### 1.1 编号格式

采用**语义化版本（Semantic Versioning）**：

```
vMAJOR.MINOR.PATCH
   主版本 . 次版本 . 修订号
```

示例：`v1.0.0` → `v1.1.0` → `v1.1.1` → `v2.0.0`。书写时正式版本可省略前缀 `v`（如配置文件中写 `1.1.0`），文档叙述统一带 `v`。

### 1.2 各位号含义与升级规则

| 位号 | 升级条件（满足任一） | 示例 |
|------|--------------------|------|
| **MAJOR 主版本** | ① 不向下兼容的数据库结构变更（删表/删列/改语义且旧数据无法迁移）；② 破坏性 API 变更（删除/改名既有路由、改变响应结构）；③ 产品形态重大改版 | `v1.x.x → v2.0.0` |
| **MINOR 次版本** | ① 向下兼容的新功能/新页面/新接口；② 数据库**可兼容**的加表、加列；③ 提示词与内容结构的新增；④ UI 体系级重构 | `v1.0.x → v1.1.0`（任务 v1.1.0-T001） |
| **PATCH 修订号** | 向下兼容的缺陷修复、文案修正、性能与稳定性修复（不改功能与结构） | `v1.1.0 → v1.1.1` |

补充规则：

- 任一高位号升级，低位号归零（如发 MINOR 时 PATCH 归零，发 MAJOR 时 MINOR/PATCH 均归零）。
- 预发布版本加后缀：`-alpha.N`、`-beta.N`、`-rc.N`（N 从 1 起），如 `v1.2.0-beta.1`；预发布版本优先级**低于**正式版本。
- 本地构建元数据可加 `+YYYYMMDD`，如 `v1.1.0+20260925`，仅作标记、不影响版本优先级。
- 不允许出现"1.0""v1"等不完整版本号。

### 1.3 版本号登记位置（升级时必须全部同步）

1. `config/app.json` 的 `version` 字段（权威来源）；
2. 《工作总结》版本表述及文末变更记录；
3. 《产品迭代规范》第五章的"版本发布历史"。

### 1.4 升级判定示例

- 任务 v1.1.0-T001：UI 整体重构 + AI 新增三个内容字段入库（兼容加列语义）→ **MINOR**：v1.0.0 → v1.1.0。
- 修复后端并发崩溃（无功能/结构变化）→ 正常应发 **PATCH**（若与 MINOR 内容同批发布则随 MINOR，不再单独发版）。
- 将来删除既有接口或要求用户清空数据库重装 → **MAJOR**：→ v2.0.0。

## 二、任务（迭代）编号规范

### 2.1 编号格式

任务编号**跟随版本号**，格式为：

```
v{MAJOR}.{MINOR}.{PATCH}-T{序号}
```

示例：`v1.1.0-T001`、`v1.2.0-T001`、`v1.1.0-T002`。

**规则：**

- **版本号段**：表示该任务所属的目标发布版本。若任务跨版本，取任务主体完成的版本。
- **序号段**：同一版本号内从 `T001` 起顺序递增，全局唯一，永不重用。
- **任务目录**：`documents/{版本号}-{任务描述}/`，例如 `documents/v1.1.0-前端视觉重构/`。
- **任务计划文档**：存放于上述目录内，文件名 `开发计划.md`。

### 2.2 编号示例

| 任务 | 编号 | 说明 |
|------|------|------|
| v1.1.0 版本首次任务（UI 重构 + AI 整段发送） | `v1.1.0-T001` | 已完成 |
| v1.2.0 版本首个任务（补全文章模块） | `v1.2.0-T001` | 待启动 |
| v1.2.0 版本第二个任务（AI 重试/缓存） | `v1.2.0-T002` | 待启动 |
| v1.1.0 版本补充修复 | `v1.1.0-T002` | PATCH 修复任务 |

### 2.3 文档引用规范

- 所有文档中提及任务时，统一使用完整编号格式，如 `v1.1.0-T001`，不简写为"任务 001"。
- 任务计划文档标题格式：`# 任务 v1.1.0-T001 · {任务描述}`。
- 任务完成后，在《工作总结》"已完成工作"章节追加记录，在《产品迭代规范》"版本发布历史"中更新。
